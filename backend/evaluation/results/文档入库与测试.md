### 根本原因

1. **PDF 是图片型课件**：文字主要是目录导航，真正内容在图片里（代码截图、讲解图）
2. **VLM 只"描述"图片外观**，没有"读取"图片中的文字：日志里 `RapidOCR returned empty result!` 反复出现，说明 OCR 对这些图片提取失败；VLM（qwen-vl-plus）描述了"六边形/立方体/标志"，但没提取出图片里的代码或知识点
3. **父子分块重复**：heading_path 只有 `['FastAPI 基础到实战']` 一层，导致多个 parent 块内容几乎相同

### 结论

项目 RAG 全链路**技术上真实生效**（解析→分块→向量化→混合检索→重排→返回），Agent Markdown 文档的检索质量良好。但 **FastAPI PDF 因其图片型课件特性**，当前多模态处理只能提取图片外观描述，无法获取图片中的知识内容，导致检索结果质量低。

### 1. Embedding 缓存（[embedding_cache.py](file:///d:/Dev/Projects/my-code-space/projects/claude-learning/education-agent/backend/app/retrieval/embedding_cache.py)）

**两层缓存架构**：
- **LRU 内存缓存**（容量 2048）：命中延迟 <0.1ms
- **磁盘持久化缓存**（JSONL 格式）：重启后仍可命中

- 缓存键 = `SHA256(text)[:16] + model_name`，避免不同模型向量混用
- `embed_batch` 批量查询缓存，仅对未命中的批量计算
- [create_embedding_model](file:///d:/Dev/Projects/my-code-space/projects/claude-learning/education-agent/backend/app/retrieval/embeddings.py#L294-L299) 默认启用缓存

## 1. ONNX 加速原理

### 原理
PyTorch 是训练框架，推理时有大量冗余（动态图、梯度追踪、Python 开销）。ONNX 把模型转成**静态计算图**，再做以下优化：

| 优化 | 说明 | 收益 |
|------|------|------|
| **算子融合** | 把多层操作（如 Attention 的 QKV）合并成一个 kernel | 减少内存读写 |
| **常量折叠** | 编译期算出常量表达式 | 省运行时计算 |
| **内核自动调优** | 针对硬件选最快实现 | CPU 上明显 |
| **去除训练开销** | 无梯度、无 autograd | 内存省 30% |

### 业界验证
- [BGE-Reranker ONNX 教程](https://adg.csdn.net/697079f3437a6b40336a6ab1.html)：ONNX 提速 30%+
- [EmbeddedLLM/bge-reranker-v2-m3-onnx-o3-cpu](https://www.promptlayer.com/models/bge-reranker-v2-m3-onnx-o3-cpu)：专门做 CPU O3 优化的 ONNX 版本
- [TensorRT 加速](https://blog.csdn.net/weixin_35578748/article/details/157537426)：GPU 上 2.45x（但需要 NVIDIA GPU）

**对你项目的结论**：CPU 环境下 ONNX 是最稳妥的方案，预期 2-3x 加速，精度无损。

## 2. 候选集数量的生产实践

第一阶段检索：100-200 候选
Rerank：top 30-50
返回 LLM：top 5-10
延迟：~80-200ms（GPU）

- 业界 30-50 是 GPU 场景，CPU 上 24 已经是合理上限
- 加候选数会线性增加 rerank 时间

## 3. 动态决定是否 rerank（置信度方案）

这个想法有学术支撑，但要谨慎：

### 学术验证
- [DynamicRAG (arxiv 2505.07233)](https://arxiv.org/html/2505.07233v2)：用 RL 优化 reranker，动态调整顺序和数量，SOTA
- [CBDR (arxiv 2509.06472)](https://arxiv.org/html/2509.06472v1)：基于 LLM 内部置信度决定是否触发检索

### 业界态度（[来源](https://ranjankumar.in/rag-engineering-reranking-precision-gap)）
> "A RAG pipeline without a reranker is not a production RAG pipeline - it is a demo."

业界强烈不建议跳过 reranker，因为：
- Reranker 减少 67% 检索失败率
- 跳过 reranker 的风险：negation、temporal、conditional 等精细场景失败

### 实用的"动态 rerank"方案
不是"是否 rerank"，而是"**rerank 多少**"：

```
方案：基于分数分布的动态 rerank

1. 拿到 vector+BM25 融合结果（24 个）
2. 看融合分数分布：
   - 如果 top1 和 top10 分数差很大（清晰查询）→ 只 rerank top 10
   - 如果 top1 和 top10 分数接近（模糊查询）→ rerank 全部 24
3. 置信度指标：top_k 分数的标准差 / 极差
```

**对你项目的结论**：可以做，但优先级低于 ONNX 加速。先 ONNX 让 rerank 变快，动态 rerank 是锦上添花。

### 关键设计决策

| 决策 | 理由 |
|------|------|
| 三级判断（规则→跳过→LLM） | 大部分查询不含指代词，规则判断避免不必要的 LLM 调用，节省成本 |
| 专用重写 LLM（temperature=0.0） | 确保相同输入产生相同输出，提高缓存命中率 |
| `max_tokens=100` | 重写查询不需要长输出，控制成本 |
| 缓存键 = `query + context_hash` | 相同 query 在不同对话上下文中重写结果不同，需独立缓存 |
| 失败静默降级 | LLM 不可用时返回原查询，不影响主流程 |
| 只取最近 6 条消息（3 轮） | 控制重写 prompt 大小，太久远的对话对指代消解帮助有限 |
