## 1. 故障现象

内存泄漏通常表现为渐进性退化，最终触发 OOM。典型现象：

- **容器 OOM Killed**：Kubernetes Pod 被 kill，状态 `OOMKilled`，重启循环
- **Java Heap OOM**：`java.lang.OutOfMemoryError: Java heap space`
- **GC 频繁**：Full GC 每分钟数次，每次耗时数秒，但内存回收不明显
- **响应变慢**：GC STW 导致请求堆积、响应时间飙升
- **类加载泄漏**：`OutOfMemoryError: Metaspace`

监控告警示例：

```
[告警] prod-user-service 内存使用率 > 90% 持续 5 分钟
当前值: 94.3%, 容器限制: 4Gi
重启次数: 3 (最近1小时)
```

## 2. Java 内存泄漏排查

### 2.1 jmap dump 堆内存

```bash
# 查看 JVM 进程
jps -l

# 查看堆内存概况
jmap -heap 12345

# 查看对象直方图（按对象大小排序）
jmap -histo:live 12345 | head -20

# 输出示例
#  num     #instances         #bytes  class name
#     1:       1234567      123456789  [Lcom.example.User;
#     2:        987654       45678901  java.util.HashMap$Node
#     3:        876543       34567890  java.lang.String

# dump 堆内存（生产环境注意会触发 STW）
jmap -dump:format=b,file=/tmp/heap_$(date +%s).hprof 12345
```

也可通过 JVM 参数配置 OOM 时自动 dump：

```
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dumps/
```

### 2.2 MAT 分析工具

[Eclipse MAT](https://www.eclipse.org/mat/) 是分析堆 dump 的标准工具。

**分析流程：**

1. 打开 hprof 文件，等待 MAT 索引构建完成
2. 查看 **Leak Suspects Report**，MAT 会自动识别可疑泄漏点
3. 查看 **Dominator Tree**，按 Retained Size 排序，找到占用内存最大的对象
4. 对可疑对象右键 → `Path To GC Roots → exclude weak/soft references`，查看为何无法回收

**Leak Suspects 报告示例：**

```
Problem Suspect 1:
The class "com.example.cache.UserCache" loaded by ...
occupies 1.2 GB (85.7%) of the heap. The memory is accumulated
in one instance of "java.util.concurrent.ConcurrentHashMap".

Problem Suspect 2:
345 instances of "org.apache.http.impl.conn.PoolingHttpClientConnectionManager"
loaded by "sun.misc.Launcher$AppClassLoader" occupy 280 MB.
```

**Dominator Tree 关键概念：**

- **Shallow Size**：对象自身占用的内存
- **Retained Size**：对象被回收后可释放的总内存（含其引用链）

### 2.3 常见泄漏模式

#### 模式 1：静态集合不断膨胀

```java
// 错误：静态 Map 持续写入，永不清理
public class UserCache {
    private static final Map<String, User> CACHE = new HashMap<>();

    public static void put(String id, User user) {
        CACHE.put(id, user);  // 内存持续增长
    }
}

// 正确：使用带 TTL 的缓存
public class UserCache {
    private static final Cache<String, User> CACHE = Caffeine.newBuilder()
            .maximumSize(100000)
            .expireAfterWrite(30, TimeUnit.MINUTES)
            .build();

    public static void put(String id, User user) {
        CACHE.put(id, user);
    }
}
```

#### 模式 2：ThreadLocal 未 remove

```java
// 错误：ThreadLocal 使用后未清理，线程池线程复用导致泄漏
public class TraceContext {
    private static final ThreadLocal<TraceInfo> HOLDER = new ThreadLocal<>();

    public void handle() {
        HOLDER.set(new TraceInfo());
        try {
            // 业务逻辑
            doBusiness();
        } finally {
            // 错误：未调用 remove
        }
    }
}

// 正确
public void handle() {
    HOLDER.set(new TraceInfo());
    try {
        doBusiness();
    } finally {
        HOLDER.remove();  // 必须在 finally 中清理
    }
}
```

#### 模式 3：监听器未移除

```java
// 错误：注册监听器后未反注册
public class EventService {
    public void register() {
        EventBus.subscribe(this::onEvent);  // 重复注册导致泄漏
    }
}

// 正确：保存引用并取消订阅
public class EventService implements Disposable {
    private final Consumer<Event> handler = this::onEvent;

    public void register() {
        EventBus.subscribe(handler);
    }

    @Override
    public void dispose() {
        EventBus.unsubscribe(handler);
    }
}
```

#### 模式 4：连接未关闭

```java
// 错误：异常情况下连接未关闭
public void query() {
    Connection conn = dataSource.getConnection();
    Statement stmt = conn.createStatement();
    ResultSet rs = stmt.executeQuery("SELECT ...");
    // 异常抛出后，conn/stmt/rs 都未关闭
    return rs.getString(1);
}

// 正确：try-with-resources 自动关闭
public void query() {
    try (Connection conn = dataSource.getConnection();
         Statement stmt = conn.createStatement();
         ResultSet rs = stmt.executeQuery("SELECT ...")) {
        return rs.getString(1);
    }
}
```

## 3. Python 内存泄漏排查

### 3.1 tracemalloc

Python 3.4+ 内置的内存跟踪模块：

```python
import tracemalloc
import linecache
import sys

# 启动跟踪
tracemalloc.start(25)  # 保存 25 帧调用栈

# 业务代码运行一段时间
run_business_logic()

# 输出当前内存占用 TOP 10
snapshot = tracemalloc.take_snapshot()
top_stats = snapshot.statistics('lineno')

print("[ Top 10 ]")
for stat in top_stats[:10]:
    frame = stat.traceback[0]
    print(f"{stat.size / 1024:.1f} KiB, {stat.count} blocks, "
          f"{frame.filename}:{frame.lineno}")
    # 打印对应行代码
    line = linecache.getline(frame.filename, frame.lineno).strip()
    if line:
        print(f"    {line}")

# 对比两次快照，找出增长点
snapshot1 = tracemalloc.take_snapshot()
# ... 业务运行
snapshot2 = tracemalloc.take_snapshot()
for stat in snapshot2.compare_to(snapshot1, 'lineno')[:10]:
    print(stat)
```

输出示例：

```
[ Top 10 ]
45.2 MiB, 123456 blocks, /app/cache.py:42
    CACHE[user_id] = load_user_from_db(user_id)
12.8 MiB, 89234 blocks, /app/parser.py:128
    result = parse_large_xml(content)
```

### 3.2 objgraph

可视化对象引用关系，定位无法回收的对象：

```python
import objgraph

# 查看对象数量 TOP
objgraph.show_most_common_types(limit=10)
# 输出: dict 123456, list 98765, function 34567

# 查看增长最多的对象
objgraph.show_growth(limit=10)

# 查看某对象到 GC Roots 的引用链
objgraph.show_backrefs([obj], max_depth=5, filename='ref.png')
```

### 3.3 常见 Python 泄漏

- **循环引用**：含 `__del__` 方法的对象循环引用无法被引用计数回收（需 GC），大量累积会泄漏
- **全局变量**：模块级 list/dict 持续 append
- **C 扩展泄漏**：C 扩展未正确释放 GIL 或内存

```python
# 错误：循环引用
class Node:
    def __init__(self):
        self.parent = None
        self.children = []

n1, n2 = Node(), Node()
n1.children.append(n2)
n2.parent = n1  # 循环引用，n1/n2 无法被引用计数回收

# 正确：使用 weakref
import weakref

class Node:
    def __init__(self):
        self._parent = None
        self.children = []

    @property
    def parent(self):
        return self._parent() if self._parent else None

    @parent.setter
    def parent(self, value):
        self._parent = weakref.ref(value) if value else None
```

## 4. Go 内存泄漏排查

### 4.1 pprof heap

```bash
# 抓取堆内存 profile
curl -o heap.out http://10.0.1.13:6060/debug/pprof/heap

# 交互分析
go tool pprof heap.out
(pprof) top 10
(pprof) list <function>
(pprof) web

# 对比两次 profile，找出增长点
curl -o heap2.out http://10.0.1.13:6060/debug/pprof/heap
go tool pprof -base heap.out heap2.out
```

### 4.2 goroutine 泄漏

Go 内存泄漏常表现为 goroutine 泄漏，goroutine 持有的内存无法回收：

```bash
# 查看 goroutine 数量
curl http://10.0.1.13:6060/debug/pprof/goroutine?debug=1 | head -20
```

**典型泄漏代码：**

```go
// 错误：channel 永远没有接收者，goroutine 阻塞泄漏
func leakyFunc() {
    ch := make(chan int)  // 无缓冲 channel
    go func() {
        val := <-ch  // 永久阻塞，goroutine 泄漏
        _ = val
    }()
    // 函数返回，ch 无接收者
}

// 正确：使用 context 控制生命周期
func worker(ctx context.Context) {
    for {
        select {
        case <-ctx.Done():
            return
        case val := <-ch:
            process(val)
        }
    }
}
```

### 4.3 escape analysis

逃逸分析帮助识别本应在栈上分配却逃逸到堆的对象：

```bash
go build -gcflags="-m -l" main.go
# 输出示例
# ./main.go:15:9: &User{} escapes to heap
# ./main.go:22:13: ... argument does not escape
```

### 5.3 JVM 容器内存设置陷阱

容器限制 4Gi，但 JVM 堆设为 4G，实际还有 Metaspace、线程栈、直接内存、GC 开销，必然 OOM。

```
# 错误
-Xmx4g

# 正确：堆内存约为容器限制的 60-70%
-Xmx2.5g -Xms2.5g
-XX:MaxMetaspaceSize=256m
-XX:ReservedCodeCacheSize=128m
-Xss512k
# 剩余约 1G 给线程栈、直接内存、GC 等使用
```

## 6. 内存分析常见模式

| 模式 | 表现 | 根因 |
| --- | --- | --- |
| 大对象驻留 | 单个对象占用数百 MB | 大缓存、大文件一次性加载 |
| 缓存膨胀 | Map/List 持续增长 | 无淘汰策略或容量上限 |
| 连接泄漏 | HttpClient/Connection 对象多 | 连接未关闭 |
| 线程泄漏 | 线程数持续增长 | 线程池未复用，无限创建 |
| 类加载器泄漏 | Metaspace 持续增长 | 动态类加载未卸载 |
| 直接内存泄漏 | 堆外内存增长 | NIO ByteBuffer 未释放 |

## 7. 应急处理

按风险优先级：

### 7.1 重启

```bash
# 优雅重启，避免影响流量
kubectl rollout restart deployment user-service -n prod
```

### 7.2 扩内存

```bash
# 临时扩容 Pod 内存
kubectl patch deployment user-service -n prod -p \
  '{"spec":{"template":{"spec":{"containers":[{"name":"app","resources":{"limits":{"memory":"8Gi"}}}]}}}}'
```

### 7.3 限流

降低流量，减缓内存增长速度，为排查争取时间。

## 8. 预防措施

### 8.1 代码审查 Checklist

- [ ] 静态集合是否有容量上限和 TTL
- [ ] ThreadLocal 是否在 finally 中 remove
- [ ] 监听器/回调是否在销毁时反注册
- [ ] Connection/Stream/Reader 是否使用 try-with-resources
- [ ] 缓存是否设置 maximumSize 和 expireAfterWrite
- [ ] 线程池是否复用，是否配置合理的队列上限
- [ ] 大对象是否分批处理，避免一次性加载
- [ ] 是否有无限增长的 Map/List

### 8.2 内存监控告警

| 指标 | 阈值 | 告警级别 |
| --- | --- | --- |
| 容器内存使用率 | > 85% 持续 5 分钟 | P2 |
| JVM 堆使用率 | > 80% | P2 |
| Full GC 频率 | > 1 次/分钟 | P1 |
| Full GC 耗时 | > 3 秒 | P2 |
| Metaspace 使用率 | > 80% | P3 |
| goroutine 数量 | > 1000 | P3 |

### 8.3 压测验证

发布前在预发环境做长时间稳定性压测（如 8 小时），观察内存是否持续增长：

```bash
# wrk 持续压测 8 小时
wrk -t8 -c500 -d28800s --latency http://api.example.com/user/info
```

若内存曲线呈阶梯式上升且不回落，需排查泄漏点。
