## 1. 系统概述

### 1.1 业务背景

公司电商平台 Nova Mall 经营服饰、3C 数码、家居、生鲜等多品类商品，业务覆盖 B2C 交易、商家入驻、营销活动、物流跟踪、售后退换货全链路。随着业务规模扩张，原单体架构在迭代效率、扩展能力、故障隔离上已无法满足要求，故启动微服务化重构。

### 1.2 用户规模与流量

### 2.2 服务间调用关系（文字版架构图）

典型下单链路：

```
客户端 → API网关 → 用户服务(鉴权)
              → 风控服务(异步, MQ)
              → 商品服务(校验商品)
              → 营销服务(计算优惠) → 促销服务(校验券)
              → 库存服务(扣减库存)
              → 订单服务(创建订单)
                  ├─ 异步通知 → 通知服务(短信/Push)
                  ├─ 异步事件 → Kafka(订单创建事件)
                  │              ├→ 营销服务(积分)
                  │              ├→ 物流服务(预生成运单)
                  │              └→ 数据中台(埋点)
                  └─ 同步调用 → 支付服务(发起支付)
                                  └→ 风控服务(支付风控)
```

支付回调链路：

```
支付渠道 → API网关 → 支付服务(回调处理)
              ├→ 订单服务(更新订单状态) → Kafka(支付成功事件)
              ├→ 库存服务(确认扣减)
              ├→ 营销服务(核销优惠券)
              └→ 通知服务(支付成功推送)
```

## 3. 技术选型

### 3.1 微服务框架对比

| 维度 | Spring Cloud Alibaba | Apache Dubbo | go-zero |
| --- | --- | --- | --- |
| 语言 | Java | Java/Go（3.0） | Go |
| 通信协议 | HTTP/REST + RPC | TCP/Dubbo 协议 | HTTP + gRPC |
| 注册中心 | Nacos | Nacos/ZK | etcd |
| 性能 | 中（HTTP 开销） | 高（二进制协议） | 极高 |
| 生态 | 完善（Spring 全家桶） | 完善 | 中等 |
| 团队学习成本 | 低（Java 团队） | 中 | 高（需 Go 技能栈） |
| 监控/治理 | 完善（Sentinel/SkyWalking） | 完善 | 内置 |

### 3.2 最终选型与理由

**核心交易服务（订单/支付/库存/用户）：Dubbo 3.0 + Nacos**

- 性能要求高，Triple 协议（基于 HTTP/2）兼顾性能与通用性
- 团队 Java 技术栈成熟，Dubbo 3.0 兼容 Spring Cloud 生态
- 强类型 RPC，便于接口契约管理

**对外 API 网关与 BFF 层：Spring Cloud Gateway**

- 协议适配灵活，支持 REST/WebSocket
- 与 Spring 生态无缝集成，过滤器链丰富

**搜索/通知等 IO 密集型服务：go-zero**

- 高并发、低内存占用
- 通知服务、搜索服务、风控服务选用

**统一治理**：Nacos（注册+配置）、Sentinel（限流熔断）、Jaeger（链路追踪）、SkyWalking（APM）。

## 4. 服务拆分

### 4.1 拆分原则

1. **领域驱动（DDD）**：按业务领域边界拆分，每个服务对应一个子域
2. **单一职责**：一个服务只做一件事，可独立部署、独立扩展
3. **数据自治**：每个服务独享数据库，不跨库 join
4. **合适的粒度**：避免过度拆分（团队规模决定边界，团队 2-pizza 原则）
5. **避免分布式事务**：通过事件驱动解耦，优先最终一致性

### 4.2 服务清单

| 服务名 | 职责 | 技术栈 | 数据存储 | 对外接口 |
| --- | --- | --- | --- | --- |
| user-service | 用户注册、登录、个人信息、地址、会员等级 | Java + Dubbo3 | MySQL（分库）+ Redis | Dubbo / REST |
| product-service | 商品 CRUD、SKU、类目、属性、上下架 | Java + Dubbo3 | MySQL + MongoDB（详情） | Dubbo / REST |
| order-service | 订单创建、查询、取消、状态机 | Java + Dubbo3 | MySQL（分库分表）+ Redis | Dubbo / REST |
| pay-service | 支付下单、渠道调用、回调、退款 | Java + Dubbo3 | MySQL + Redis | Dubbo / REST |
| stock-service | 库存查询、扣减、回滚、对账 | Java + Dubbo3 | MySQL + Redis（预扣） | Dubbo |
| search-service | 商品搜索、聚合、推荐召回 | Go + go-zero | Elasticsearch | REST |
| promo-service | 优惠券、满减、秒杀、活动 | Java + Dubbo3 | MySQL + Redis | Dubbo / REST |
| logistics-service | 物流下单、轨迹查询、运单管理 | Java + Dubbo3 | MySQL | Dubbo / REST |
| notify-service | 短信、Push、站内信、邮件 | Go + go-zero | MySQL + Kafka | REST / Kafka |
| risk-service | 注册风控、交易风控、反欺诈 | Go + go-zero | MySQL + Redis + Flink | REST / Kafka |
| marketing-service | 积分、会员权益、用户标签 | Java + Dubbo3 | MySQL + HBase | Dubbo |

### 4.3 拆分边界示例

**订单与库存的边界**：订单服务负责订单生命周期（创建、待支付、已支付、已发货、已完成、取消、退款），不直接操作库存数据。库存扣减通过同步 RPC 调用 stock-service，库存确认通过支付成功事件异步处理。

**订单与支付的边界**：订单服务生成订单后调用 pay-service 发起支付，但订单状态不直接由订单服务改为"已支付"，而是由 pay-service 回调成功后通过事件通知 order-service 更新。这避免了订单服务对支付状态的强依赖。

### 5.1 方案对比

- 支持 AP/CP 切换，交易服务用 CP 保证强一致，边缘服务用 AP
- 长连接（gRPC）推送，减少心跳压力
- 与 Dubbo 3.0、Spring Cloud Alibaba 深度集成

## 8. 服务间通信

### 8.1 通信方式选型

| 场景 | 通信方式 | 选型理由 |
| --- | --- | --- |
| 同步强依赖（下单/扣库存） | Dubbo RPC | 强类型、低延迟、可同步返回结果 |
| 弱依赖/异步通知 | Kafka MQ | 解耦、削峰、可重试 |
| 跨语言调用 | gRPC / REST | 标准协议、跨语言支持 |
| 实时推送 | WebSocket | 长连接双向通信 |

### 8.2 同步调用注意事项

- 必须设置合理超时（Dubbo `timeout`）：核心接口 1s，非核心 3s
- 必须配置重试次数：幂等接口可重试，非幂等接口禁止重试
- 必须配置降级方案：`mock=force:return null` 或自定义 fallback
- 必须配置熔断：Sentinel 资源规则

### 8.3 异步事件驱动

订单创建事件示例：

```java
// 订单服务发布事件
@Service
public class OrderService {
    @Autowired private RocketMQTemplate mqTemplate;

    public Order createOrder(OrderRequest req) {
        Order order = buildAndSave(req);
        // 发送事务消息，保证与本地事务一致
        mqTemplate.sendMessageInTransaction(
            "order-topic",
            MessageBuilder.withPayload(new OrderCreatedEvent(order)).build(),
            order.getId()
        );
        return order;
    }
}

// 营销服务消费事件（积分发放）
@RocketMQMessageListener(topic = "order-topic", consumerGroup = "marketing-cg")
public class OrderEventListener implements RocketMQListener<OrderCreatedEvent> {
    @Override
    public void onMessage(OrderCreatedEvent event) {
        pointsService.awardPoints(event.getUserId(), event.getAmount());
    }
}
```

事件契约存放在独立的 `event-contract` 仓库，由架构组统一治理。

## 9. 数据一致性

### 9.1 分布式事务方案对比

| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 |
| --- | --- | --- | --- | --- |
| 2PC | 强一致 | 差 | 中 | 数据库层（少用） |
| TCC | 强一致 | 中 | 高 | 资金、库存 |
| Saga | 最终一致 | 好 | 中 | 长流程业务 |
| 事务消息 | 最终一致 | 极好 | 低 | 异步解耦场景 |
| 本地消息表 | 最终一致 | 好 | 低 | 简单异步 |

### 9.2 订单创建 Saga 流程

订单创建涉及 4 个服务的分布式事务，采用 Saga 编排模式：

```
正向流程（Saga 执行）
  T1 订单服务: 创建订单(状态=待处理)         ← 已支付前置
  T2 库存服务: 预扣库存
  T3 营销服务: 锁定优惠券
  T4 用户服务: 冻结余额(若使用余额支付)

补偿流程（任一失败时反向执行）
  C4 用户服务: 解冻余额
  C3 营销服务: 释放优惠券
  C2 库存服务: 回滚预扣
  C1 订单服务: 标记订单=已取消
```

Saga 编排器实现（基于状态机引擎）：

```java
@Service
public class CreateOrderSaga {
    public void execute(OrderRequest req) {
        SagaContext ctx = new SagaContext(req);
        try {
            t1CreateOrder(ctx);              // T1
            t2DeductStock(ctx);              // T2
            t3LockCoupon(ctx);               // T3
            t4FreezeBalance(ctx);            // T4
            ctx.markSuccess();
        } catch (Exception e) {
            compensate(ctx);                 // 反向补偿
        }
    }

    private void compensate(SagaContext ctx) {
        if (ctx.t4Done) userClient.unfreezeBalance(ctx);
        if (ctx.t3Done) promoClient.releaseCoupon(ctx);
        if (ctx.t2Done) stockClient.rollbackDeduct(ctx);
        if (ctx.t1Done) orderClient.cancelOrder(ctx);
    }
}
```

### 9.3 库存扣减采用 TCC

库存扣减要求强一致，采用 TCC：

```java
// Try：预扣减
@TwoPhaseBusinessAction(name = "deductStock", commitMethod = "commit", rollbackMethod = "rollback")
public boolean tryDeduct(BusinessActionContext ctx, String sku, int qty) {
    // 检查并冻结库存（freeze 字段 + qty）
    return stockMapper.freeze(sku, qty) > 0;
}

// Confirm：确认扣减
public boolean commit(BusinessActionContext ctx) {
    String sku = ctx.getActionContext("sku").toString();
    int qty = ctx.getActionContext("qty");
    // 冻结 → 实际扣减
    return stockMapper.confirmDeduct(sku, qty) > 0;
}

// Cancel：取消
public boolean rollback(BusinessActionContext ctx) {
    String sku = ctx.getActionContext("sku").toString();
    int qty = ctx.getActionContext("qty");
    // 解冻
    return stockMapper.unfreeze(sku, qty) > 0;
}
```

## 10. 容错设计

### 10.1 熔断降级（Sentinel）

```java
@SentinelResource(value = "queryProduct",
    blockHandler = "queryProductBlockHandler",
    fallback = "queryProductFallback")
public Product queryProduct(Long productId) {
    return productService.query(productId);
}

// 限流后返回
public Product queryProductBlockHandler(Long id, BlockException ex) {
    return Product.degraded();     // 返回降级商品
}

// 异常后兜底
public Product queryProductFallback(Long id, Throwable t) {
    return cacheService.getFromCache(id);   // 从缓存兜底
```

## 11. 链路追踪

### 11.1 方案选择

采用 **Jaeger**（CNCF 毕业项目），原因：
- 原生支持 OpenTracing / OpenTelemetry
- 与 Dubbo、Spring Cloud 集成良好
- UI 友好，支持依赖拓扑图
- 比 Zipkin 性能更优（Cassandra/ES 后端）

### 11.2 采样率配置

```yaml
# 采样策略
tracing:
  sampling:
    type: probabilistic
    param: 0.1            # 全局 10% 采样
  # 异常请求强制采样
  forced: 
    - http.status >= 500
    - rpc.error != null
```

- 生产环境默认 10% 采样，降低存储成本
- 错误请求 100% 采样，便于问题定位
- 大促期间临时下调到 1%，保护链路系统

### 11.3 traceId 透传

```java
// Dubbo Filter 透传 traceId
@Activate(group = {CommonConstants.PROVIDER, CommonConstants.CONSUMER})
public class TraceFilter implements Filter {
    @Override
    public Result invoke(Invoker<?> invoker, Invocation invocation) {
        String traceId = RpcContext.getContext().getAttachment("traceId");
        if (traceId == null) {
            traceId = MDC.get("traceId");
        }
        RpcContext.getContext().setAttachment("traceId", traceId);
        return invoker.invoke(invocation);
    }
}
```

traceId 贯穿网关 → Dubbo → Kafka（通过 Header 透传） → 下游服务，最终在 Jaeger 上展示完整调用链。

## 12. 数据存储设计

### 12.1 分库分表策略

订单表按 `user_id` 分库分表：8 库 × 32 表 = 256 张表，单表控制在 2000 万行内。

```java
// ShardingSphere 配置
shardingsphere:
  sharding:
    tables:
      t_order:
        actual-data-nodes: ds${0..7}.t_order_${0..31}
        database-strategy:
          complex:
            sharding-columns: user_id
            algorithm-class: OrderDbShardingAlgorithm
        table-strategy:
          complex:
            sharding-columns: user_id
            algorithm-class: OrderTableShardingAlgorithm
        key-generator:
          column: order_id
          type: SNOWFLAKE
```

### 12.2 多存储选型

| 数据类型 | 存储 | 理由 |
| --- | --- | --- |
| 交易数据 | MySQL（分库分表） | 强一致 |
| 商品详情 | MongoDB | 灵活 Schema |
| 商品搜索 | Elasticsearch | 倒排索引、聚合 |
| 用户会话 | Redis Cluster | 低延迟 |
| 库存预扣 | Redis + Lua | 原子操作 |
| 操作日志 | Kafka → S3/ODPS | 海量归档 |
| 链路数据 | Jaeger → ES | 时序查询 |
| 标签画像 | HBase | 列式存储 |
