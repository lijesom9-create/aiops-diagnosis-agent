## 1. 审查流程

代码审查（Code Review，简称 CR）是保证代码质量、传播知识、防止"巴士因子"风险的关键实践。团队统一采用 PR/MR 驱动的审查流程。

### 1.1 流程步骤

1. **PR 提交**：开发者完成开发与自测，从 feature 分支向目标分支提交 PR。
2. **自动检查**：CI 自动运行 lint、单元测试、覆盖率、安全扫描，全部通过后进入人工审查队列。
3. **人工审查**：1-2 名 Reviewer 进行审查，提出修改建议或批准。
4. **修改迭代**：作者根据反馈修改代码，再次推送，触发新一轮 CI 与审查。
5. **批准合并**：Reviewer 给出 Approve 后，作者或维护者执行合并（默认 Squash merge）。

### 1.2 时效要求

| 阶段 | 时效 |
|------|------|
| Reviewer 首次响应 | 工作日 4 小时内 |
| 修改后再次审查 | 工作日 2 小时内 |
| 紧急 hotfix PR | 30 分钟内 |

### 1.3 角色职责

| 角色 | 职责 |
|------|------|
| 作者（Author） | 提供清晰的 PR 描述、自测通过、响应反馈 |
| 审查者（Reviewer） | 严肃对待审查、提供建设性反馈、按时响应 |
| 维护者（Maintainer） | 最终合并决策、解决冲突与争议 |

## 2. 审查标准 Checklist

Reviewer 在审查时应对照以下清单逐项检查。PR 作者在提交前也应自检。

### 2.1 功能正确性

- [ ] 代码是否真正实现了 PR 描述中声明的功能？
- [ ] 是否处理了所有边界条件（空值、零值、最大值、超长字符串）？
- [ ] 是否考虑了并发场景（多用户同时操作、重复点击）？
- [ ] 是否与产品需求文档一致？

### 2.2 边界条件

- [ ] 列表为空时是否正常返回？
- [ ] 数值越界（如负数、超大数）是否被处理？
- [ ] 字符串包含特殊字符（emoji、SQL 关键字）是否安全？
- [ ] 时间处理是否考虑了时区与跨天场景？

### 2.3 错误处理

- [ ] 异常是否被正确捕获和处理，而不是被 `pass` 吞掉？
- [ ] 错误信息是否对用户友好且不泄露系统内部细节？
- [ ] 是否记录了足够的日志用于排查问题？
- [ ] 外部依赖（数据库、第三方 API）失败时是否有降级方案？

### 2.4 安全性

- [ ] 是否存在 SQL 注入风险（拼接 SQL）？
- [ ] 用户输入是否经过校验与转义？
- [ ] 敏感信息（密码、Token、身份证）是否在日志中被脱敏？
- [ ] 权限校验是否到位（用户能否访问他人数据）？
- [ ] 依赖项是否有已知漏洞（CI 安全扫描）？

### 2.5 性能

- [ ] 是否存在 N+1 查询问题？
- [ ] 循环内是否避免了不必要的数据库或网络调用？
- [ ] 大列表查询是否使用了分页？
- [ ] 是否引入了不必要的全表扫描？
- [ ] 缓存使用是否合理（缓存键、过期时间、一致性）？

### 2.6 可读性

- [ ] 命名是否清晰表达意图？
- [ ] 函数是否过长（超过 50 行需关注）？
- [ ] 复杂逻辑是否有注释说明"为什么"这样实现？
- [ ] 是否存在过度设计（YAGNI 原则）？

### 2.7 测试覆盖

- [ ] 新功能是否有对应的单元测试？
- [ ] 测试是否覆盖了正常路径与异常路径？
- [ ] 测试覆盖率是否达到 80% 以上？
- [ ] 测试是否独立可重复运行（不依赖外部状态）？

## 3. 审查礼仪

代码审查的本质是协作而非评判，良好的礼仪是高效协作的基础。

### 3.1 建设性反馈

- 对事不对人，评价代码而非作者。
- 用"我们"代替"你"，体现团队共同责任。
- 解释"为什么"，而不只是指出"是什么"。

### 3.2 具体建议

- 提供可操作的建议，而非模糊的批评。
- 必要时给出代码示例。

### 3.3 区分必须改与建议改

为避免审查反馈含糊，团队统一使用以下标记：

| 标记 | 含义 | 作者处理方式 |
|------|------|--------------|
| `[must]` | 必须修改：Bug、安全漏洞、不符合规范 | 必须修改并回复 |
| `[suggest]` | 建议修改：可优化的设计、命名 | 建议采纳，可讨论 |
| `[question]` | 提问：理解代码意图 | 必须回复说明 |
| `[nit]` | 吹毛求疵：格式、拼写等小问题 | 可选修改 |
| `[praise]` | 赞赏：值得学习的优秀写法 | 无需处理 |

### 3.4 礼仪反面示例

```
# 错误：攻击性、模糊
这代码写得真烂，重新写吧。
你这个逻辑根本不对。
看不懂你在写什么。
```

```
# 正确：建设性、具体
[must] 这里如果 user_id 为 None 会抛出 AttributeError，
建议在调用前做空值校验：

    if user_id is None:
        raise InvalidParamError("user_id 不能为空")

[suggest] 这个函数有 80 行，建议拆分为 _validate_input
和 _execute_query 两个子函数，可读性更好。
```

## 4. 常见问题模式

### 4.1 命名问题

```python
# 反面：命名无意义
def process(data):
    result = do_something(data)
    return result

# 正面：命名表达意图
def calculate_order_total(order_items: list[OrderItem]) -> int:
    total = sum(item.subtotal for item in order_items)
    return total
```

### 4.2 圈复杂度过高

```python
# 反面：嵌套过深，圈复杂度高
def get_discount(user, order):
    if user is not None:
        if user.is_vip:
            if order.total > 1000:
                if order.items_count > 5:
                    return 0.8
                else:
                    return 0.85
            else:
                return 0.9
        else:
            return 1.0
    else:
        return 1.0

# 正面：提前返回，扁平化
def get_discount(user: User | None, order: Order) -> float:
    if user is None or not user.is_vip:
        return 1.0
    if order.total <= 1000:
        return 0.9
    return 0.8 if order.items_count > 5 else 0.85
```

### 4.3 重复代码

```python
# 反面：重复的校验逻辑
def create_user(data):
    if not data.get("username"):
        raise ValueError("username 必填")
    if not data.get("email"):
        raise ValueError("email 必填")
    if not data.get("phone"):
        raise ValueError("phone 必填")
    # ...

def update_user(data):
    if not data.get("username"):
        raise ValueError("username 必填")
    if not data.get("email"):
        raise ValueError("email 必填")
    # ...

# 正面：提取公共校验
REQUIRED_USER_FIELDS = ["username", "email", "phone"]

def validate_user_data(data: dict) -> None:
    for field in REQUIRED_USER_FIELDS:
        if not data.get(field):
            raise ValueError(f"{field} 必填")
```

### 4.4 硬编码

```python
# 反面：硬编码的魔法数字与字符串
if retry_count > 3:
    time.sleep(5)

# 正面：提取为常量
MAX_RETRY_COUNT = 3
RETRY_INTERVAL_SECONDS = 5

if retry_count > MAX_RETRY_COUNT:
    time.sleep(RETRY_INTERVAL_SECONDS)
```

### 4.5 资源泄漏

```python
# 反面：未关闭文件/连接
def read_config(path: str) -> str:
    f = open(path, "r")
    return f.read()  # 异常时不会关闭

# 正面：使用上下文管理器
def read_config(path: str) -> str:
    with open(path, "r", encoding="utf-8") as f:
        return f.read()
```

### 4.6 并发问题

```python
# 反面：竞态条件
counter = 0
def increment():
    global counter
    counter += 1  # 非原子操作，多线程下会丢失更新

# 正面：使用锁
import threading
counter = 0
lock = threading.Lock()

def increment():
    global counter
    with lock:
        counter += 1
```

## 5. 审查评论模板

### 5.1 通用模板

```
[标记] 简要描述问题

**问题**：具体说明哪里有问题、为什么是问题。
**建议**：给出具体的修改方案或代码示例。
**影响**：说明不修改可能导致的后果（可选）。
```

### 5.2 常用话术

**指出 Bug：**
```
[must] 这里存在空指针风险

**问题**：当 user.profile 为 None 时，访问 user.profile.avatar
会抛出 AttributeError，线上已有类似案例（参考 PROJ-1234）。
**建议**：使用安全访问：
    avatar = user.profile.avatar if user.profile else None
```

**建议优化：**
```
[suggest] 可以使用列表推导式简化代码

**问题**：当前用 for 循环拼接列表，Python 风格上更推荐推导式。
**建议**：
    emails = [u.email for u in users if u.is_active]
```

**提问：**
```
[question] 这里为什么用 sleep 而不是事件通知？

**问题**：sleep(5) 会让线程阻塞，在高并发下会耗尽线程池。
是有特殊原因吗？如果是等待外部状态，建议用 Redis 的 pub/sub
或消息队列。
```

**赞赏：**
```
[praise] 这个状态机设计很清晰

把状态流转抽象为 FSM 引擎，新增状态只需配置转移表，
后续维护成本很低，值得在订单服务中推广。
```

### 5.3 批准合并的话术

```
LGTM (Looks Good To Me)

代码逻辑清晰，测试覆盖完整，CI 全绿。
[must] 的 2 个问题已修复。可以合并。
```

```
Approved with nits

[nit] 第 42 行多了一个空行，合并前可顺手清理。
其余无问题，可以合并。
```

## 6. 审查工具

### 6.1 工具对比

| 工具 | 平台 | 特点 |
|------|------|------|
| GitHub Pull Request | GitHub | 行级评论、CI 集成、Approve 机制 |
| GitLab Merge Request | GitLab | 支持 Code Quality 报告、Discussion 可Resolved |
| Reviewable | 第三方 | 基于 GitHub，提供更精细的 diff 与文件级审查 |
| Gerrit | 独立 | 提交级审查，适合内核级项目 |
| Phabricator | 独立 | Differential 审查，已逐步被 GitLab 替代 |

### 6.2 GitHub PR 最佳实践

- PR 描述使用模板，包含：背景、改动点、测试方式、关联工单。
- 单个 PR 控制在 400 行以内，大改动拆分为多个 PR。
- 使用 `Reviewers` 显式指定审查者，避免无人响应。
- 使用 `Labels` 标注 PR 类型（feature/bug/hotfix）与状态。

### 6.3 PR 描述模板

```markdown
## 背景
<!-- 简述需求背景与 PR 目的 -->
为支持手机号登录，新增短信验证码服务。

## 改动点
<!-- 列出主要改动 -->
- 新增 SmsService 类
- 用户登录接口增加 captcha 字段
- 补充单元测试 12 个

## 测试方式
<!-- 如何验证 -->
- 运行 `pytest tests/test_sms_service.py`
- 本地启动后调用 POST /api/v1/users/login，传入 captcha 参数

## 关联工单
Closes PROJ-1234

## Checklist
- [x] 通过 lint 与单元测试
- [x] 覆盖率 ≥ 80%
- [x] 更新了相关文档
- [x] 无硬编码的密钥或环境信息
```

## 7. 审查度量

为持续改进审查质量，团队按月统计以下指标：

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 平均审查响应时间 | < 4 小时 | 首次响应时长 |
| 平均 PR 合并时长 | < 24 小时 | 提交到合并 |
| PR 平均改动行数 | < 400 行 | 控制单次审查负担 |
| 每个 PR 平均评论数 | 3-8 条 | 过少可能审查不充分，过多可能 PR 过大 |
| 审查引入的缺陷率 | < 5% | 合并后 1 周内发现的问题占比 |

## 8. 常见误区

### 8.1 把审查当"橡皮图章"

**误区**：Reviewer 不仔细看代码，直接 Approve。

**后果**：审查流于形式，质量问题仍进入主分支。

**改进**：Reviewer 应认真阅读每一行代码，至少在本地 mental run 一遍逻辑。

### 8.2 在审查中讨论架构

**误区**：在 PR 评论中讨论系统架构设计，导致讨论发散、合并延迟。

**改进**：架构问题应在设计阶段（RFC 或技术方案评审）解决，PR 审查聚焦实现细节。若发现重大架构问题，应关闭 PR，先做方案评审。

### 8.3 追求完美导致无法合并

**误区**：Reviewer 提出大量 `[suggest]`，作者反复修改，PR 数周无法合并。

**改进**：区分 must 与 suggest，`suggest` 可创建后续 issue 跟进，不应阻塞当前 PR。

### 8.4 审查者代替作者写代码

**误区**：Reviewer 直接给出大段代码，作者直接复制粘贴。

**后果**：作者未真正理解，且责任归属模糊。

**改进**：Reviewer 给出思路与示例，由作者自行实现并理解。
