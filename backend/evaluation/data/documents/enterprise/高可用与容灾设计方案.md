# 高可用与容灾设计方案

| 文档属性 | 内容 |
| --- | --- |
| 文档分类 | architecture |
| 文档版本 | v2.3 |
| 适用范围 | 核心交易系统、用户中心、支付服务 |
| 维护人 | SRE 架构组 |

## 1. 高可用目标

公司核心交易系统的可用性目标为 **SLA 99.99%**，即全年故障时间不超过 52.6 分钟。围绕该目标定义核心容灾指标：

| 指标 | 定义 | 目标值 |
| --- | --- | --- |
| SLA | 服务可用时间 / 总时间 | 99.99% |
| RTO（Recovery Time Objective） | 故障发生后到服务恢复的最大允许时间 | ≤ 5 分钟 |
| RPO（Recovery Point Objective） | 故障发生时允许丢失的最大数据量 | ≤ 30 秒 |

可用性等级划分：

- **L0 核心交易**：SLA 99.99%，必须同城双活 + 异地灾备
- **L1 重要业务**：SLA 99.95%，同城双活
- **L2 一般业务**：SLA 99.9%，主备模式

## 2. 多可用区部署

### 2.1 同城双活架构

同城双活采用"两可用区 + 双写 + 全局负载均衡"模式，可用区 A（主）与可用区 B（备）距离 ≤ 30km，网络延迟 ≤ 2ms。

```
                     [全局 DNS / GTM]
                    /                \
            [可用区 A - 主]        [可用区 B - 备]
            /      |     \         /      |     \
       [SLB-A] [SLB-A] [SLB-A] [SLB-B] [SLB-B] [SLB-B]
         |       |       |       |       |       |
       [App集群A1..A6]         [App集群B1..B6]
            \      /                \      /
        [MySQL MGR 主] <==同步== [MySQL MGR 备]
        [Redis Cluster 分片1..N 跨可用区分布]
        [Kafka Cluster 跨可用区分布]
```

设计要点：

1. 应用层无状态，可在两个可用区同时承载流量
2. 数据库采用 MGR（MySQL Group Replication）单主模式，跨可用区同步复制
3. Redis Cluster 的 master 与 slave 分布在不同可用区
4. Kafka 配置 `min.insync.replicas=2`，副本分布在两个可用区
5. 全局流量管理器（GTM）按地理位置和健康度动态调度流量，默认 A 区 70%、B 区 30%

### 2.2 异地灾备

异地灾备机房位于 1000km 外的城市，采用异步复制模式，应对整体机房级故障：

- 数据库：基于 binlog 的异步复制（DTS/Canal），延迟通常 < 30 秒
- 对象存储：跨区域复制（如 OSS 跨区域复制）
- 配置中心：配置数据定时快照上传至异地
- 切换策略：仅在主机房整体不可用时启用，RTO ≤ 30 分钟，RPO ≤ 1 分钟

## 3. 负载均衡设计

采用四层 + 七层的多层负载均衡架构：

### 3.1 四层负载（LVS / 云 SLB）

- 入口流量通过云 SLB（基于 LVS + Keepalived）做四层转发，DR 模式
- 健康检查配置：TCP 8080 端口，间隔 2 秒，连续 3 次失败摘除
- 会话保持关闭（应用无状态）

### 3.2 七层负载（Nginx）

```nginx
upstream backend_api {
    least_conn;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=30s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=30s;
    server 10.0.2.11:8080 max_fails=3 fail_timeout=30s backup;
    keepalive 32;
}

server {
    listen 80;
    server_name api.example.com;

    location /api/ {
        proxy_pass http://backend_api;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_connect_timeout 2s;
        proxy_read_timeout 30s;
        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_next_upstream_tries 2;
    }

    location /health {
        access_log off;
        return 200 "ok\n";
    }
}
```

关键参数说明：

- `least_conn`：最小连接数策略，避免长请求堆积
- `max_fails=3 fail_timeout=30s`：30 秒内失败 3 次标记不可用
- `proxy_next_upstream`：失败自动重试下一台，仅对幂等请求开启
- `keepalive 32`：与后端保持长连接，降低握手开销

## 4. 数据库高可用

### 4.1 选型对比

| 方案 | 一致性 | 写性能 | 自动切换 | 适用场景 |
| --- | --- | --- | --- | --- |
| MySQL 主从 + MHA | 异步 | 高 | 半自动 | 中小规模 |
| MySQL MGR | 强一致 | 中 | 自动 | 金融交易 |
| TiDB | 强一致 | 高（分布式） | 自动 | 海量数据 |
| Redis Sentinel | 异步 | 高 | 自动 | 缓存 |
| Redis Cluster | 异步 | 高 | 自动 | 大规模缓存 |

### 4.2 MySQL MGR 配置

核心交易库采用 MGR 单主模式，3 节点跨可用区部署：

```ini
# my.cnf 关键配置
[mysqld]
server_id=1
gtid_mode=ON
enforce_gtid_consistency=ON
binlog_format=ROW
binlog_row_image=FULL

# MGR 配置
plugin_load_add='group_replication.so'
group_replication_group_name="aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa"
group_replication_local_address="10.0.1.21:33061"
group_replication_group_seeds="10.0.1.21:33061,10.0.2.21:33061,10.0.1.22:33061"
group_replication_bootstrap_group=OFF
group_replication_single_primary_mode=ON
group_replication_enforce_update_everywhere_checks=OFF
transaction_write_set_extraction=XXHASH64
group_replication_transaction_size_limit=150000000
```

### 4.3 Redis Cluster

Redis Cluster 采用 6 主 6 从，master 与 slave 跨可用区分布：

```conf
# redis.conf
cluster-enabled yes
cluster-config-file nodes-6379.conf
cluster-node-timeout 5000
cluster-replica-validity-factor 10
cluster-migration-barrier 1
cluster-require-full-coverage no
appendonly yes
appendfsync everysec
```

## 5. 消息队列高可用

### 5.1 Kafka 集群

- 6 Broker 跨可用区部署，副本因子 3，`min.insync.replicas=2`
- 生产者配置 `acks=all`，确保消息写入多数副本后才确认
- 消费者配置自动提交关闭，业务处理完成后手动提交 offset

```properties
# producer 关键配置
acks=all
retries=2147483647
max.in.flight.requests.per.connection=5
enable.idempotence=true
compression.type=lz4
```

### 5.2 RocketMQ DLedger

对消息顺序性和事务要求高的场景采用 RocketMQ DLedger 模式，基于 Raft 协议实现自动主从切换：

```properties
# broker.conf
brokerClusterName=PayCluster
brokerName=broker-a
brokerId=0
dledgerGroup=group-a
dledgerPeers=n0-10.0.1.31:40911;n1-10.0.2.31:40911;n2-10.0.1.32:40911
dledgerRole= follower
enableDLegerCommitLog=true
```

## 6. 缓存高可用

### 6.1 多级缓存

```
请求 → 本地缓存(Caffeine) → 分布式缓存(Redis Cluster) → 数据库
```

本地缓存容量小（< 100MB），TTL 短（< 60s）；分布式缓存作为主缓存，TTL 较长（5-30 分钟）。

### 6.2 缓存三大问题及解决方案

#### 缓存穿透（查不存在的数据）

恶意请求查询不存在的 key，每次都打到数据库。

**方案 1：空值缓存**

```python
def get_user(user_id: str):
    cache_key = f"user:{user_id}"
    value = redis.get(cache_key)
    if value is not None:
        if value == "NULL":
            return None  # 命中空值标记
        return json.loads(value)
    # 未命中，查数据库
    user = db.query_user(user_id)
    if user is None:
        redis.set(cache_key, "NULL", ex=60)  # 空值缓存 60 秒
        return None
    redis.set(cache_key, json.dumps(user), ex=1800)
    return user
```

**方案 2：布隆过滤器**（对海量不存在的 key 更高效）

```python
from pybloom_live import ScalableBloomFilter

bloom = ScalableBloomFilter(initial_capacity=1000000, error_rate=0.001)

def init_bloom():
    for user_id in db.query_all_user_ids():
        bloom.add(user_id)

def get_user_safe(user_id: str):
    if user_id not in bloom:
        return None  # 布隆过滤器拦截
    return get_user(user_id)
```

#### 缓存击穿（热点 key 过期）

单个热点 key 过期瞬间，大量请求同时打到数据库。

**方案：互斥锁 + 永不过期 + 异步刷新**

```python
import threading
import time

lock = threading.Lock()

def get_hot_data(key: str):
    value = redis.get(key)
    if value is not None:
        return json.loads(value)
    # 加锁重建
    if lock.acquire(blocking=False):
        try:
            # 双重检查
            value = redis.get(key)
            if value is not None:
                return json.loads(value)
            data = db.query(key)
            redis.set(key, json.dumps(data), ex=1800)
            return data
        finally:
            lock.release()
    else:
        # 未抢到锁，短暂等待后重试
        time.sleep(0.05)
        return get_hot_data(key)
```

#### 缓存雪崩（大量 key 同时过期）

大量 key 在同一时刻过期，或 Redis 整体宕机。

**方案 1：过期时间随机化**

```python
import random

def cache_set(key: str, value, base_ttl: int = 1800):
    ttl = base_ttl + random.randint(0, 300)  # 基础 TTL + 0~300 秒随机偏移
    redis.set(key, json.dumps(value), ex=ttl)
```

**方案 2：多级缓存兜底 + 熔断降级**

当数据库压力过大时，触发熔断，返回降级数据（默认值/本地缓存）。

## 7. 服务无状态化改造

无状态化是横向扩展和故障切换的前提。改造清单：

1. **Session 外置**：Tomcat/Jetty 的 Session 迁移到 Redis（Spring Session）
2. **本地缓存清理**：应用内本地缓存仅做读优化，失效时间 < 60s，避免数据不一致
3. **文件存储迁移**：上传文件统一存对象存储（OSS/S3），禁止写入本地磁盘
4. **定时任务去重**：使用分布式锁（Redisson）或 XXL-JOB 调度，避免多实例重复执行

Spring Session 配置示例：

```yaml
spring:
  session:
    store-type: redis
    redis:
      namespace: spring:session
      flush-mode: on_save
  redis:
    host: redis-cluster.example.com
    port: 6379
```

## 8. 容灾切换流程

完整切换流程：**故障检测 → 决策 → 切换 → 验证 → 回切**

1. **故障检测**：监控探针每 5 秒探测，连续 3 次失败触发告警
2. **决策**：值班 SRE 确认故障范围，根据决策矩阵选择切换策略
3. **切换**：GTM 切换流量、数据库主备切换、DNS TTL 调整
4. **验证**：核心链路冒烟测试（登录、下单、支付）
5. **回切**：原主机房恢复后灰度切回，避免二次故障

### 容灾切换决策矩阵

| 故障类型 | 切换策略 | 预计耗时 | RPO |
| --- | --- | --- | --- |
| 单实例宕机 | 自动摘除，集群自愈 | 30 秒 | 0 |
| 单可用区故障 | GTM 切流至另一可用区 | 2 分钟 | 0 |
| 数据库主节点故障 | MGR 自动选主 | 10-30 秒 | 0 |
| Redis 主节点故障 | Cluster 自动 failover | 10-30 秒 | < 1 秒 |
| 整机房故障 | 异地灾备接管 | 15-30 分钟 | < 1 分钟 |
| 区域网络故障 | 切换至异地灾备 | 15-30 分钟 | < 1 分钟 |

## 9. 混沌工程

通过故障注入演练验证系统韧性，每季度一次全链路演练。

### 9.1 工具选型

- **ChaosBlade**：阿里开源故障注入工具，支持 CPU、网络、磁盘、进程等故障
- **ChaosMesh**：Kubernetes 原生混沌工程平台

### 9.2 演练流程

1. **场景设计**：根据故障树分析（FTA）设计演练场景
2. **爆炸半径控制**：先在灰度环境演练，再逐步扩大到生产
3. **故障注入**：使用 ChaosBlade 注入故障

```bash
# 注入 CPU 飙高（占用 80% CPU）
blade create cpu load --cpu-percent 80

# 注入网络延迟（对数据库 10.0.1.21 延迟 2 秒）
blade create network delay --time 2000 --interface eth0 --remote-port 3306 --destination-ip 10.0.1.21

# 注入网络丢包（对支付服务丢包 50%）
blade create network loss --percent 50 --interface eth0 --destination-ip 10.0.2.31

# 模拟 Pod 故障
blade create k8s pod-pause --namespaces prod --labels app=payment

# 销毁实验
blade destroy <experiment_id>
```

4. **监控观测**：观察告警、自动切换、降级是否按预期生效
5. **复盘改进**：填写演练报告，记录发现的薄弱点，跟踪改进项至闭环

## 10. 附录：监控告警

关键监控指标与告警阈值：

| 指标 | 阈值 | 持续时间 | 告警级别 |
| --- | --- | --- | --- |
| 接口 P99 延迟 | > 500ms | 1 分钟 | P2 |
| 接口错误率 | > 1% | 1 分钟 | P1 |
| CPU 使用率 | > 80% | 3 分钟 | P2 |
| 数据库连接数 | > 80% 上限 | 1 分钟 | P1 |
| Redis 内存使用 | > 80% | 5 分钟 | P2 |
| Kafka 消费延迟 | > 10000 条 | 2 分钟 | P2 |

告警通知通过钉钉机器人 + 电话语音双通道触达值班人员，P1 故障需 5 分钟内响应。
