## 1. 安全加固（评估 4/10 → 致命洞清零）

### 1.1 注册接口提权漏洞（致命）

- **问题**：`POST /api/auth/register` 的请求体允许自传 `role="admin"`，`register_user` 无任何拦截——任何匿名用户一条请求即成为管理员，接管全部管理端点。`api/auth.py:53` + `core/auth.py:228`。
- **方案**：从源头移除"客户端自选角色"。`UserCreate` / `RegisterRequest` 删除 role 字段；注册角色由代码决定——固定 `student`，仅当用户名匹配 `SUPER_ADMIN_USERNAME` 时授予 admin（保留超管初始化）；后续提权走角色管理 API 或 `promote_admin.py`。
- **前端对齐**：注册页移除学生/教师选择器（此前选教师实际也只注册成 student，属 UI 误导）；`RegisterRequest` 类型删除 role 字段——TS 编译期封死，防止日后从前端塞回。
- **文件**：`backend/app/core/auth.py`、`backend/app/api/auth.py`、`frontend/src/types/index.ts`、`frontend/src/components/Auth/RegisterPage.tsx`。

### 1.2 知识库端点越权（高危）

- **问题**：`GET/DELETE /api/knowledge/documents/{id}` 任意登录用户可读/删任意文档向量数据；同项目 `documents.py` 的同类删除却有 admin 校验——同一操作两套标准。chunk 内容含跨组织数据。
- **方案**：三个端点（stats/读取/删除）统一收紧到 `require_admin`。
- **文件**：`backend/app/api/knowledge.py`。

### 1.3 告警 webhook 无鉴权（高危）

- **问题**：`POST /api/alerts/webhook` 完全公开——任何人可伪造告警推送飞书（污染告警可信度）或刷飞书 API 配额；`/alerts/test` 同样公开。
- **方案**：共享密钥 `ALERT_WEBHOOK_SECRET`（config 新增），请求经 `Authorization: Bearer`（Alertmanager 原生支持）或 `X-Webhook-Secret` 头携带，`hmac.compare_digest` 比对防时序侧信道；**未配置密钥时端点直接 503 拒绝**（secure by default）。`/alerts/test` 加 `require_admin`。四处配置同步：`alertmanager/alertmanager.yml`（http_config.authorization）、`docker-compose.yml`、三个 `.env.example`。
- **文件**：`backend/app/api/alerts.py`、`backend/app/core/config.py`、`alertmanager/alertmanager.yml`、`docker-compose.yml`、`backend/.env*.example`。

### 1.4 登录/注册无限流（高危）

- **问题**：`rate_limit_dep` 按用户 ID 限流且未认证请求直接放行——登录/注册可无限暴力破解。
- **方案**：新增 `auth_rate_limit_dep` 按客户端 IP 限流（`AUTH_RATE_LIMIT_PER_MIN`，默认 20 次/分，支持 X-Forwarded-For 适配反代），接入注册与登录端点。
- **顺手修复的真 bug**：Redis 限流实现把 `zadd` 放在超限判断之前——**被拒绝的请求也计入窗口**，用户越刷锁得越久；改为先统计、未超限才写入。
- **文件**：`backend/app/core/rate_limiter.py`、`backend/app/api/auth.py`。

### 1.5 未修复（有意识取舍）

JWT 无服务端吊销（logout 仅删 cookie）——需 token 版本号/blacklist 机制，影响面大，记录为已知债务。

## 3. 业务闭环（评估结论：六个结构性缺口）

### 缺口 1：触发模型反了（pull → push）—— 产品成立与否的关键

- **问题**：真实运维是事件驱动（"凌晨三点告警响了"），系统却要用户打开聊天框提问；告警链路推完飞书卡片就断。
- **方案**：告警 webhook → 自动调用 Agent 诊断（BackgroundTasks）→ 结构化诊断报告作为第二张卡片推送飞书。诊断输入由告警 labels/annotations 构造；`session_id` 按事故隔离。
- **文件**：`backend/app/api/alerts.py`、`backend/app/notify/feishu.py`（`build_diagnosis_card`：橙色卡片，根因/置信度/处置方案，底部固定"🤖 AI 自动诊断，供参考，处置前请人工确认"）。

### 缺口 2：时间窗盲区 + 变更事件缺失

- **问题**：`query_metrics` 无时间参数（真实故障诊断几乎都是回顾性："半小时前开始报错，那段时间指标长什么样"）；无变更事件源（变更 = 生产故障第一大根因，运维诊断第一个问题永远是"过去一小时改了什么"）。
- **方案**：`query_metrics` 加 `time_range`——短窗口（≤2h）返回故障瞬时值、长窗口（6h/24h）返回均值，LLM 可推理"长窗口正常 + 短窗口异常 = 近期突发"；新工具 `get_recent_changes(service, hours)` 返回发布/配置变更/扩缩容事件，mock 与种子事故对齐（payment-service 事发前 40 分钟发版）；prompt 新增**阶段 2C 变更检查**（"变更先于深挖"）。二者均不进 `_MOCK_MONITORING_TOOLS` 剔除集合——MCP 启用时存活（变更/拓扑本无现成真实源，mock 是有意为之）。
- **文件**：`backend/app/langgraph_agent/tools.py`、`agent.py`（prompt）。

### 缺口 4：知识库生命周期没有答案

- **问题**：语料与考卷同源（206 篇语料与评测集同一脚本产出——循环验证）；系统强制要求 frontmatter 标注但真实文档不会带；retry 端点重试时不回传 `extra_metadata`（重试后 chunk 丢业务元数据，检索命中不到）；负反馈 API 存在但反馈 → 知识库更新的环是断的。
- **方案**：`infer_business_metadata(filename, title, content_head)` 规则推断 doc_type/service（INC- 前缀→incident、复盘→postmortem、预案→sop 等；service 无高置信命中不编造），标记 `source=auto_inferred` 便于复核；插入点选 `uploader._store_chunks` **单点**（天然覆盖 API/批量/Celery/降级/种子脚本全部路径）；retry 从 Mongo 文档记录取回 `extra_metadata` 回传（顺手修的完整性 bug）；feedback 请求支持 `document_ids`，点踩将引用文档标记 `needs_review=true`（含原因与关联反馈 ID），feedback 写入改走 `Database.save_feedback` 消除裸写 `db._mongo`。
- **文件**：`backend/app/document/frontmatter.py`、`uploader.py`、`api/documents.py`、`api/langgraph.py`、`core/database.py`。

### 缺口 5：信任与验证

- **问题**：评测集与 mock 语料同源（循环）；监控数据/架构信息发给外部 LLM 无审计留痕。
- **方案**：真实公开事故回放集 `agent_eval_scenarios_real.json`（Cloudflare 2019 正则回溯 / GitLab 2017 误删库 / AWS 2021 重试风暴 / Facebook 2021 BGP 断网，带 disclaimer），`agent_eval.py` 加 `--scenarios-file` 参数、报告单独落盘不污染 mock 主报告——诚实展示"知识库无先验时"的能力边界；**工具调用审计**：`run()` 结束后将本次全部工具调用（工具名 + 参数截断 + user_id + session_id + intent）写入 Mongo `tool_audit_logs`，审计失败不影响诊断主链路。
- **文件**：`backend/evaluation/eval/agent_eval.py`、`evaluation/data/agent_eval_scenarios_real.json`、`langgraph_agent/agent.py`、`core/database.py`。

### 缺口 6：诊断到行动的最后一公里

- **方案**：`create_incident_ticket` 工单工具（返回 TK- 编号，演示环境标注）；prompt 约定"仅 P1/P2 或用户明确要求时调用，诊断中途不调用"；不入证据白名单（工单回执不是证据）。

### 缺口 3：观测深度（APM/调用链/业务指标）

明确不做——需真实 APM 基础设施，文档记录为演进方向。

## 4. 事故生命周期（"一次告警一次诊断" → "事故全流程跟进"）

### 4.1 问题：诊断时机与事故演化规律冲突

- 告警 fire 的 T+0 诊断一次即结束，但真实事故证据随时间展开（连接池可能 5 分钟后才打满）；15 分钟冷却期内不再看第二次；冷却坑在诊断前就占——诊断失败（LLM 超时）也静默失效。
- 现状的成本模型也错：冷却按 fingerprint，一次真实事故的 3-10 条告警各自触发**全量诊断**且互不共享上下文——告警风暴才是成本的最大受害者。

### 4.2 方案：Incident 实体 + 三段式状态机

```
新 fingerprint → 创建 incident（Mongo）→ 全量初诊
同 service 关联窗口内新告警 → 归入（升级信号）→ 增量重诊
已知 fingerprint 心跳（间隔满足 + 低置信）→ 增量重诊
resolved 后 FLAPPING_WINDOW 内复燃 → 重新打开原事故（不重诊）
全部 resolved → 安静期确认不复燃 → 恢复摘要 → 闭案
```

- **成本护栏**（默认内置）：重诊硬上限 `DIAG_MAX_REDIAG_PER_INCIDENT=3`；severity 门槛 `ALERT_MIN_SEVERITY`（LLM 前零成本拦截）；**增量重诊**（上次报告 + 新证据，要求"确认/修正/推翻"三选一，1-2 次调用替代全量）；抖动复用 `INCIDENT_FLAPPING_WINDOW=1800s`。**告警数与诊断成本脱钩**：N 条告警聚合 1 个事故 1 次初诊。
- **服务映射**：`_extract_service` 按 `service label > job > instance 主机名` 分层提取 + `ALERT_SERVICE_MAP` 静态覆盖（告警规则无 service 标签的环境）。
- **恢复摘要**：时间线 + 历次诊断结论演变 + 根因确认 + 复盘草稿（绿色卡片），incident.summary 落库——接上"事故 → 复盘 → 知识 → 下次诊断"的知识回流环。
- **飞书卡片**按触发类型显示：🩺 自动诊断 / 🔁 诊断更新（事故升级）/ 🔁 持续跟踪 / ✅ 恢复摘要。

### 4.3 文件与验证

- `alerts.py`（路由/护栏/摘要）、`core/database.py`（incidents 注册表 8 方法，双分支模式）、`config.py`（6 项配置）、`notify/feishu.py`（卡片）、`tests/test_incident_lifecycle.py`（25 条：路由四级/护栏幂等/同批聚合一次诊断/增量 prompt/安静期复燃取消摘要）。

## 5. 执行层可靠性（三个执行层问题）

### 5.1 诊断任务不可恢复（BackgroundTasks 进程内，重启静默丢失）

- **方案**：诊断任务落 **Mongo `diagnosis_tasks`**，worker 消费循环（lifespan 启动/关闭取消，事件唤醒 + 5s 轮询兜底）：
  - FIFO **原子认领**：`find_one_and_update(status=pending → running)`——单文档原子性即跨实例互斥，多副本不重复诊断；
  - 失败**退避重试**（`DIAG_TASK_RETRY_BACKOFF_SECONDS=60`，回队后窗口内不可认领）、达 `DIAG_TASK_MAX_ATTEMPTS=3` 标 dead 留痕；
  - **启动捞回**：lifespan 将僵尸 running（`DIAG_TASK_STALE_SECONDS=900s`）重置 pending，重启不丢诊断；
  - **中断续跑**：重试的初诊走"继续完成"提示——checkpoint 保留半途对话现场（含已完成取证），从断点接着诊断。
- **测试驱动出的真修正**：最初失败回队后 drain 循环立刻再消费同一任务——瞬时 LLM 故障几秒内烧光重试次数直接 dead；引入退避窗口后瞬时故障被真正吸收。
- **为什么不 Celery**：任务表覆盖其 90% 收益（持久化/重试/不重复消费），且无跨进程重建 Agent/knowledge_store 成本；按吞吐量（每小时几个事故）做的判断。

### 5.2 单实例天花板

- SQLite checkpoint 单文件锁钉死单副本 → **`CHECKPOINT_BACKEND=mongodb`**（compose 生产默认）：会话现场与事故/任务数据同库全集群共享；初始化失败降级 MemorySaver 不阻塞启动。依赖同步：`langgraph-checkpoint-mongodb==0.4.0`、pymongo 4.17→4.16、pydantic 2.12.5→2.13.5（新依赖硬性约束，否则全新安装依赖冲突）。
- Semaphore(1)/冷却的进程内问题：认领机制 + DB 态 incident 计数天然解决；Semaphore 降级为单实例本地并发上限。

### 5.3 自动诊断看不到私有文档

- **问题**：可见性过滤是"公共文档 OR 本人文档"，自动诊断以 `user_id="alert-webhook"` 检索——各团队标注 service 的私有运维文档（最有价值的部分）全部不可见。
- **方案两步**：`DIAGNOSIS_ORG_ID` 服务身份 org 注入（新增 `_current_org_id` contextvar，从 task_context 贯穿到检索层）；文档级 `shared_to_diagnosis` 标记（字符串 "true"/"false"，单/批上传 Form 字段，admin 上传默认共享、敏感文档可关闭）随 chunk metadata 入库。
- **语义精确性**：`可见 = shared OR (org 条件 AND user 条件)`——不能三条件全 OR（否则"别人组织下的他人私有文档"漏出，安全回归）；未共享文档隔离语义与原来完全一致；Qdrant pre-filter 翻译器扩展 `$or` 嵌套组（递归解析成嵌套 Filter）与 Python post-filter 双层一致，均有测试锁定。

| **知识库时效/冲突**（三年前旧 SOP 与新方案并存被等权召回；两个 postmortem 结论冲突无仲裁） | `valid_until` 过期文档 rerank 后**软降权 ×0.5**（不硬过滤——覆盖优先），引用列表与 LLM 上下文标注"⚠️ 已过有效期，仅供参考"；`effective_date` 支持 prompt 层历史冲突**取更新者**并注明冲突（不做 NLI 自动仲裁——误判污染诊断，交给知识库运营流程）；字段进 `BUSINESS_FIELDS` 走 frontmatter→extra_metadata 全路径 |

- **方案**：liveness/readiness 分离——`/live` 保留为进程存活探针（恒真是正确语义）；新增 `/api/health/ready` 真实探测 Mongo（ping）/Redis（配置了才探测，挂了标记 degraded 而非不就绪——内存降级仍可服务）/Qdrant 知识库；compose HEALTHCHECK 切换到 `/ready`；删除 main.py 死路由。

## 11. 有意识不做的取舍（面试叙事素材）

1. **Celery 化诊断**：任务表原子认领 + 恢复覆盖其 90% 收益，且无跨进程重建 Agent/knowledge_store 成本——按吞吐量（小时级事故量）判断；
2. **知识图谱**：诊断查询 90% 是一跳查找，拓扑 JSON 覆盖（~1% 成本拿走 90% 价值）；多跳场景设三个成熟触发条件（真实拓扑数据源 / 真实复盘语料规模 / 评测证明多跳系统性失败）之前不投入；图谱的维护腐烂问题（过期图谱以"结构化事实"身份污染推理）比文档过期更危险；
3. **自动冲突仲裁（NLI）**：误判污染诊断，交给知识库运营流程 + prompt 层"取更新者"；
4. **反事实推理验证变更因果**：超出当前模型能力，prompt 论证义务已够；
5. **JWT 服务端吊销**：需 token 版本号/blacklist，记录为已知债务；
6. **巨型类重构 / God-class 拆分**（unified_store/agent.py 2000+ 行、database.py 86 方法）：重构风险大于展示收益，企业级阶段再还债；
7. **APM/tracing**：需真实基础设施，文档记录为演进方向；
8. **mypy 全量类型检查**：44k 行存量的多日工程，ruff 先行，mypy 渐进。
