## 二、R1：demo-payment-sim（被诊断的真实服务）

### 2.1 定位与设计原则

**不是玩具脚本，而是"被诊断的真实对象"**——它的真实性决定诊断的真实性。三条设计原则：

1. **真实连接池语义**：SQLAlchemy `QueuePool(pool_size=5, max_overflow=0, pool_timeout=3)`——连接被占满后，第 6 个请求**真实阻塞 3 秒**后抛 `TimeoutError` → 未处理异常 → 500。与生产 HikariCP 耗尽行为同构（含 "QueuePool limit reached" 风格日志）。
2. **真实指标命名空间**：`demo_*` 前缀（取代 mock 时代的 `error_rate`/`connection_pool_usage` 命名）——指标名表见 §2.3，Agent 经知识库文档（M2-R4）学习这些名字。
3. **真实流量**：后台线程每 ~0.5s 产生一次真实 HTTP 下单 + 70% 概率支付——无外部压测工具时指标/告警也能自然流动。

### 2.2 端点清单

**业务面**：

| 端点 | 说明 |
|------|------|
| `POST /orders` | 下单（写 SQLite，模拟 5-20ms 基线耗时） |
| `POST /pay/{id}` | 支付（读单 → 标记 → 写支付记录） |
| `GET /orders/{id}` | 查单 |
| `GET /healthz` | 存活 + 数据库连通（真实探活碰存储） |
| `GET /metrics` | Prometheus 指标 |

**控制面**（故障注入，见 §三）：

| 端点 | 说明 |
|------|------|
| `POST /_faults/{name}/on` | 注入故障（body 为参数） |
| `POST /_faults/{name}/off` | 解除 |
| `GET /_faults` | 状态查询 |

### 2.3 指标命名表（诊断 Agent 的"真实世界词汇表"）

| 指标 | 类型 | 标签 | 用途 |
|------|------|------|------|
| `demo_http_requests_total` | Counter | method/path/status | 请求计数（错误率分子/分母） |
| `demo_http_request_duration_seconds` | Histogram | method/path | 延迟分布（P95/P99） |
| `demo_orders_total` | Counter | — | 下单量 |
| `demo_payments_total` | Counter | status | 支付结果（success/failed/not_found） |
| `demo_db_pool_checked_out` | Gauge | — | 连接池借出数（饱和度，上限 5） |
| `process_resident_memory_bytes` | Gauge | — | 进程常驻内存（prometheus_client 默认） |

### 2.4 技术要点

- SQLite + WAL + busy_timeout（避免写锁放大池压力）；DB 文件落 volume（`demo-data`）
- Dockerfile：python:3.12-slim、非 root、HEALTHCHECK 用 python urllib 碰 `/healthz`（slim 无 curl）
- compose：`mem_limit: 256m`（使内存泄漏故障可真实触发 OOM）、端口 8001（控制面对外，业务面容器内）

## 三、R2：故障注入工具集

| 故障 | 参数 | 触发的告警（R3） | 有机症状链 |
|------|------|----------------|-----------|
| `slow_query` | `{"delay": 2.0}` | DemoServiceHighLatency | 业务处理阻塞 → P95 飙升 → 连接持有变长 → 池压力 |
| `error_storm` | `{}` | DemoServiceHighErrorRate | /pay 全部 500 → 错误率 >30% |
| `pool_exhaustion` | `{}` | DemoServicePoolSaturation（先行）→ DemoServiceHighErrorRate | 占满 5 连接 → 请求 3s 超时 500 |
| `memory_leak` | `{"step_mb": 8}` | DemoServiceMemoryHigh →（OOM）DemoServiceDown | 每秒 +8MB → RSS 超 200MB → 容器触顶重启 |
| `dependency_timeout` | `{"delay": 5.0}` | DemoServiceHighLatency | /orders 阻塞（模拟下游风控服务挂） |

**关键设计**：注入状态只存在于进程内存 + 控制端点，**刻意不进入 Prometheus 指标**——诊断 Agent 只应看到有机症状（延迟/错误/池饱和度），不能通过 `demo_fault_active` 直接读答案。

注入示例：

```bash
curl -X POST http://localhost:8001/_faults/slow_query/on \
     -H "Content-Type: application/json" -d '{"delay": 2.0}'
curl -X POST http://localhost:8001/_faults/slow_query/off
```

## 四、R3：真实告警规则（`demo_service_alerts` 组，5 条）

| 告警 | 表达式要点 | 级别 | 触发场景 |
|------|-----------|------|---------|
| DemoServiceHighErrorRate | 5xx 占比 > 30% 持续 1m | critical | error_storm / pool_exhaustion |
| DemoServiceHighLatency | P95 > 1s 持续 2m（基线 ~20ms） | warning | slow_query / dependency_timeout |
| DemoServicePoolSaturation | `demo_db_pool_checked_out >= 5` 持续 1m | warning | pool_exhaustion **先行信号** |
| DemoServiceDown | `up == 0` 持续 1m | critical | 崩溃 / OOM |
| DemoServiceMemoryHigh | RSS > 200MB 持续 3m（容器上限 256m） | warning | memory_leak |

**对齐点**：所有规则带 `labels.service: payment-sim`——与告警路由的服务提取约定直接对齐，告警到达即可正确归入 `service=payment-sim` 的事故。

## 五、A1：事故认领（ack）语义

- **接口**：`POST /api/incidents/{id}/ack`（首认领生效、幂等——二次认领不覆盖首认领人）；`GET /api/incidents/{id}` 事故详情（诊断历史/认领信息对登录用户开放）
- **语义**：业界事故三态 triggered → acknowledged → resolved 的中间态补齐；`acked_at - first_seen_at` 即 **MTTA**，上盘 `ops_incident_mtta_seconds{service}` 直方图
- **实现**：`incidents.py` 独立路由模块；`database.py` `ack_incident`（首认领不覆盖）
- **测试**：`test_incidents_api.py` 5 条（401/首认领/幂等/404/详情字段）

## 六、A3 + B1 + B2

- **A3 runbook 附链**：诊断完成后检索 `service + doc_type=sop` top1，卡片附"📎 推荐 SOP"（不经 LLM 零成本；知识库未初始化或无命中返回 None 宁缺勿错；服务过滤无结果时降级为通用 SOP 查询）
- **B1 路由指标**：`ops_alert_route_total{level=fingerprint|flap|join|new}`——四级路由每一分支埋点，误合并（join 异常高）与碎片化（new 异常高）从不可见变可测量
- **B2 唯一索引**：Mongo partial unique index `{service, status:"active"}`——同服务并发创建第二个活跃事故被 **DB 层拒绝**；路由层捕获 `DuplicateKeyError` 后转为归入该事故（escalation）；内存模式模拟同语义（可测）
