### 0.1 产品定位（2026-09 确认，双轨）

**最终目的**：让每次生产告警响起的瞬间自动拥有基于证据、带引用溯源的初诊报告——定位从"从零找线索"变成"验证假设"，经验从个人脑子变成组织资产。
**解决的需求**：MTTR 中占 50-70% 的"定位空转段"；三个受益方——on-call 响应者（初诊/验证假设）、团队（知识资产化）、管理者（MTTA/降噪率/采纳率可度量）。
**边界**：辅助不替代（不做自动执行修复）、不做监控采集本体、不保证根因正确（给假设+证据+置信度）、不管告警源头设计。
**价值假设链**：H1 已知故障模式初诊命中（agent\_eval 已度量）→ H2 响应者采纳（需 A1 ack 才能度量）→ H3 定位段时间缩短（M1 后度量）。

### 0.3 最大未知数（比任何已列缺口都重要，R1-R3 先行的原因）

真实数据流过诊断管线时大概率暴露的适配问题——只有跑一遍才会暴露：

1. **证据解析器的 mock 耦合**：`agent.py::_parse_metrics_evidence` 为兼容 mock 写了五种格式分支——真实 Prometheus 返回结构、真实指标命名（`http_requests_total` 而非 mock 的 `error_rate`）能否被解析成证据看板，未知；

3. **日志格式**：mock 日志是构造的关键词（HikariPool），真实服务日志的结构/关键字/噪声完全不同，`query_logs` 定向检索效果未知。

## 工作流 R：诊断对象真实化（双轨核心，最优先）

> **产品定位决策**（2026-09 确认）：双轨——真实落地验证 + 语义补齐并行。

### R1. 真实示例服务（demo-payment-sim）

- **改动点**：新增 `demo-service/`（FastAPI 小服务）——下单/支付两个接口 + SQLite 存储 + 连接池（有真实上限）+ prometheus\_client 指标（RED 三件套：请求计数/错误计数/延迟直方图）+ 结构化日志输出；接入 compose（prometheus 采集、promtail 采日志）。

- **要求**：代码质量按真实标准写（不是玩具脚本）——它是被诊断的对象，它的真实性决定诊断的真实性。

- **改动点**：`prometheus/alert_rules.yml` 增加 demo-service 的 RED 告警（5xx 错误率、P95 延迟、实例存活）——阈值基于真实基线调定，非拍脑袋。

## 工作流 A：事故管理语义补齐（调研 P0，最优先）

> 依据：业界事故三态 triggered → acknowledged → resolved、MTTA 指标、复盘六段模板、runbook-attach-to-service。目标：事故管理语义与业界对齐，诊断从"广播"变成"可跟踪的协作对象"。

### A1. 事故认领（ack）语义 ⭐ 最高价值

- **改动点**：

  - `database.py`：incidents 增加 `acked_by / acked_at` 字段 + `ack_incident(incident_id, user)` 方法；

  - 新增 `POST /api/incidents/{id}/ack`（认证用户即可 ack，记录 user\_id/时间）；

  - `admin-frontend` 事故视图加认领按钮（可选，API 先行）；

  - MTTA 计算：`acked_at - first_seen_at`，随自观测指标上盘（Gauge：最近 N 事故的 MTTA）。

- **飞书卡片按钮说明**：卡片按钮回调需在飞书开放平台配置消息卡片请求网址（含加解密签名验证），成本高于 API 方案——**MVP 先 API + 管理后台**，按钮回调作为二期。

- **验收标准**：ack 后 incident 落库 `acked_by/acked_at`；重复 ack 幂等；MTTA 可从 Mongo 聚合得出。

- **成本**：0.5-1 天。

### A2. 恢复摘要模板对齐业界 + Action Items 结构化

- **改动点**：

  - `_build_summary_prompt`（agent.py）改造：要求输出 **Impact**（受影响服务/级别/持续时长，从 incident 字段聚合）+ **Action Items** 按**检测/预防/缓解**分类，每项 `{item, owner, priority, deadline}`；

  - 摘要解析：新增 `_parse_action_items(content)`（markdown list → 结构化数组），落 `incidents.action_items`；

  - 新增 `PATCH /api/incidents/{id}/actions/{index}` 更新行动项状态（pending → done）；

  - 卡片渲染行动项列表（含状态标记）。

- **验收标准**：摘要含 Impact 与分类行动项；行动项可独立更新状态；质量标准对齐业界——"完成它是否会改变系统"、"不留孤儿行动项"。

- **成本**：1-1.5 天。

### A3. 诊断卡片自动附 runbook/SOP

- **改动点**：`_process_diagnosis_task` 诊断完成后，用 `knowledge_store.hybrid_search_parent_child(query=f"{service} 处置预案", service=service, metadata_filter={"doc_type": "sop"})` 取 top1，卡片追加"📎 推荐 SOP：{title}"（不经过 LLM，零额外推理成本；链接为文档标题 + doc\_id，管理后台可查）。

- **验收标准**：有 SOP 命中的服务诊断卡片带推荐；无命中不显示（宁缺勿错）。

- **成本**：0.5 天。

### A4. 降噪率口径补齐

- **改动点**：

  - webhook 处理时新增计数器 `ops_alerts_received_total{status}`（firing/resolved 分开）；

  - 新增 `ops_incidents_created_total`；

  - 降噪压缩比 = 1 - (事故数/告警数)（Grafana 面板 + PromQL：`1 - rate(ops_incidents_created_total[1h]) / rate(ops_alerts_received_total[1h])`）。

- **验收标准**：看板能看到"原始告警 → 事故卷积"的压缩比（行业核心 KPI，调研报告 §2 的口径）。

- **✅ 已交付**（2026-09-04）：新增 `monitoring/grafana/dashboards/ops-incident-ops.json`——降噪压缩比/告警接收/事故创建/路由级别(B1)/MTTA(P95+avg) 五面板；指标采集端 `ops_alerts_received_total`/`ops_incidents_created_total`/`ops_alert_route_total`/`ops_incident_mtta_seconds` 早已就位。

- **成本**：0.5 天。

## 工作流 B：路由与关联加固（调研 P1）

> 依据：路由四级中"服务归入"是启发式无强保障（评估已识别创建竞态与跨服务碎片）；BigPanda 式根因打分；ITIL 影响度×紧急度。

### B1. 路由级别指标 `ops_alert_route_total{level=fingerprint|flap|join|new}`

- **改动点**：`_route_alert_to_incident` 每个分支埋点。**价值：误路由从"不可见"变"可测量"**——join 占比异常升高 = 误合并信号；new 占比异常升高 = 服务映射失效信号。这是后续一切路由优化的前置（先能测量再谈改进）。

- **成本**：0.5 天。

### B2. active 事故唯一部分索引（消灭创建竞态）

- **改动点**：Mongo `incidents.create_index([("service",1),("status",1)], unique=True, partialFilterExpression={"status":"active"})`（lifespan 或 database.connect 后建索引）；`_route_alert_to_incident` 捕获 `DuplicateKeyError` → 改为归入该事故（escalation）。

- **验收标准**：并发新建同服务事故只有一个成功，另一个被拒绝并转为归入。

- **成本**：0.5 天。

### B3. 服务重要性矩阵（影响度 × 紧急度 → P1-P4）

- **改动点**：`config.py` 增加 `SERVICE_CRITICALITY`（JSON：{"payment-service": "critical", "user-service": "normal"}）；告警影响等级 = 服务关键度 × 告警级别（矩阵文档化进 docs）；消费点：诊断卡片显示影响等级、escalation 判定用影响等级而非原始 severity。

- **依据**：ITIL"优先级 = 影响度 × 紧急度"；业界共识"分级矩阵事故前写死"。

- **成本**：0.5-1 天。

### B4. incident 内主嫌疑告警标记（culprit）

- **改动点**：诊断完成后规则选主嫌疑——时间最早 + 级别最高 + root\_cause 关键词与告警 summary 匹配打分，取最高分；写入 `incidents.culprit_fingerprint`，卡片标注"🎯 主嫌疑告警"。

- **依据**：BigPanda 根因打分的规则版（Open Box 可解释）。

- **成本**：0.5-1 天。

### B5. 维护窗口/静默感知

- **改动点**：路由时查 `get_recent_changes`（计划内变更窗口）——窗口内的告警在 incident 上标记 `planned_change: true`，诊断 prompt 注入"存在计划内变更，区分变更引发 vs 独立故障"。

- **依据**：PagerDuty suppressions/maintenance windows；变更管理数据的反向应用。

- **成本**：1 天。

**工作流 B 合计：3-4 天。**

### B6. 事故卡死保护（真实链路实测发现）

- **问题**：incident 的闭案依赖全部成员 fingerprint 收到 resolved——成员告警在源头被删/AM 重启丢状态/手动 webhook 测试时，事故永远停留 active。

- **修复**：① `POST /api/incidents/{id}/force-resolve`（管理员，强制闭案）；② worker 定期扫描：active 事故 `last_seen_at` 超过 N 小时（默认 6h）→ 自动闭案（标记 auto\_resolved）。

- **成本**：0.5 天。

### B7. 摘要行动项解析鲁棒性（真实链路实测发现）

- **问题**：deepseek-flash 对 `_build_summary_prompt` 的六段格式遵循不稳定——实测摘要全文未含"行动项"章节，`_parse_action_items` 返回空。

- **修复**：① prompt 中行动项改为独立强制末段并给一行示例；② `_generate_incident_summary` 解析为空时，追加一次"仅输出行动项列表（按格式）"的定向重试；③ 仍为空则记录 warning（可观测）。

- **成本**：0.5 天。

## 工作流 C：安全与可靠性债务清偿（历次评估遗留）

> 依据：安全评估 4/10 中的已知缺口、代码评估定位的并发缺陷。这些不是新功能，是"声称的安全/可靠性"的完整性。

### C1. JWT 服务端吊销（token 版本号方案）

- **改动点**：users 集合加 `token_version`（默认 0）；签发时写入 claim；`get_current_user` 校验 token\_version 与库中一致，不一致 401；logout 时 `$inc token_version`（使该用户所有旧 token 失效）；promote/改密同样递增。

- **验收标准**：logout 后旧 token 立即失效（30 分钟窗口消失）；改密后旧会话全失效。

- **成本**：1 天。

### C2. sanitizer 代码块脱敏旁路修复

- **问题**（评估已定位）：`sanitizer.py` 的 `_replace_sensitive` 对 \`\`\` 代码块与行内代码**原样保留**——LLM 输出只要把敏感数据放进代码块即绕过脱敏。

- **方案**：代码块内容不再无条件豁免——对代码块内的**高置信模式**（API key/AWS key/私钥头）仍执行脱敏，普通文本模式（手机号/身份证）豁免保留（代码块中可能是测试数据）；或提供 `SANITIZER_SANITIZE_CODE=strict/loose` 开关，生产默认 strict。

- **成本**：0.5 天。

### C3. circuit\_breaker 持锁 sleep 修复

- **问题**：令牌桶在持有 `asyncio.Lock` 期间 `await asyncio.sleep(wait)`——所有等待者串行化（代码注释自认"简化处理"）。

- **方案**：等待者不持锁 sleep——锁内只做"计算需等待的时长并登记唤醒事件"，锁外 sleep 后重新竞争。

- **成本**：0.5 天。

### C4. prompt\_guard 间接注入扫描（RAG 内容）

- **问题**：prompt\_guard 只检测用户消息，**RAG 检索回的文档内容不扫描**——投毒文档可进 LLM context。

- **方案**：在 `search_knowledge` 返回文本上复用 prompt\_guard 的规则引擎（medium 以上告警 + 日志记录，**不拦截**——拦截会误伤正常运维文档；记录 + 报告中标注"来源内容触发注入规则"）。

- **成本**：1 天。

### C5. mypy 渐进接入

- **方案**：`pyproject.toml` 加 mypy 配置（exclude 第三方/评测），**仅对** **`app/core/`** **+** **`app/api/`** **新代码目录启用非阻塞检查**进 CI（continue-on-error 起步），存量 44k 行不做全量。

- **成本**：0.5 天起步。

**工作流 C 合计：3.5 天。**
