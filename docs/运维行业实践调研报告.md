# 真实运维概念与场景调研报告

> 目的：在继续改动项目前，把项目的设计决策对齐到真实运维行业的概念体系和实践标准，识别语义缺口与改进机会。
>
> **信息来源与局限**：本报告基于 Google SRE 手册（sre.google/books，2016-2018）、ITIL 4、PagerDuty / Atlassian / Datadog / BigPanda / Moogsoft 等厂商公开文档中的**稳定行业实践**整理。调研期间实时网页检索不可用（搜索接口返回知识摘要、直接抓取超时），产品级细节（版本、具体功能名）建议以各官方文档为准；行业基础实践（事故生命周期、分级、复盘文化、告警降噪管线）近十年高度稳定，对本报告结论影响有限。

## 一、事故管理：生命周期与分级

### 1.1 业界标准生命周期

业界通行的事故生命周期是五段（ITIL 4 / Google SRE Workbook / PagerDuty 共识）：

```
Detected（检测）→ Triaged（分诊：定级、定位响应人）→ Responded（响应：止血）
→ Resolved（恢复：服务完全恢复并经监控确认）→ Reviewed（复盘：48-72h 内 blameless postmortem）
```

PagerDuty 的事故状态机是三态：**triggered → acknowledged → resolved**。

**关键概念：acknowledged（认领）**。告警发出到有人认领之间存在 `MTTA`（Mean Time To Acknowledge）——这是业界衡量值班响应质量的第一指标。认领意味着"有人接管了"，它把告警从"广播状态"变为"处理中状态"，避免多人重复响应或无人响应。

### 1.2 分级标准：按影响，不按根因

业界分级矩阵的**第一原则是按用户/业务影响分级，而非根因或指标阈值**：

| 级别 | 定义 | 响应方式 |
|------|------|---------|
| P1/SEV-1 | 核心功能完全不可用、数据丢失、安全事件；影响全部/大部分用户 | 立即 page、24/7 响应、升级通知、作战室 |
| P2/SEV-2 | 核心功能严重降级；影响部分用户；有临时方案 | 工作时间紧急 page，非工作时间升级 |
| P3/SEV-3 | 影响有限、有简单绕行方案 | 工作时间工单处理 |
| P4/SEV-4 | 可忽略影响 | 批量/积压处理 |

另一个行业共识：**分级矩阵必须在事故发生前写下来并达成共识**（written down and agreed on before incidents happen），避免事故中现场争论定级。

### 1.3 角色分工（大型事故）

Google SRE 定义三个角色：**Incident Commander**（协调决策，不动手修）、**Operations Lead**（动手操作）、**Communications Lead**（对内对外沟通、状态页更新）；换班时显式交接 IC 角色。适用前提是多人协作的大事故——单人/小团队场景可降级为"一人分饰"。

### 1.4 对照本项目：三个语义缺口

| 业界概念 | 本项目现状 | 缺口 |
|---------|-----------|------|
| acknowledged（认领） | **缺失**。诊断卡片推送后，没有"谁看过/是否采纳"的记录——事故停留在广播状态 | **最值得补的语义**：认领语义打通 MTTA 统计和"诊断采纳率"（项目已有 feedback API，缺的是事故级的 ack 动作） |
| 按影响分级 | severity 来自告警规则标签（warning/critical），是**信号强度**不是**影响等级** | 可做"服务重要性 × 告警级别"的分级映射矩阵（payment-service 的 warning 可能等于 user-service 的 P3） |
| 事故角色/频道 | 单人卡片推送 | 飞书话题/群自动创建是自然扩展（大型事故才需要，暂缓） |

## 二、告警管理与降噪：业界标准管线

### 2.1 五段降噪管线（AIOps 厂商共识架构）

BigPanda / Moogsoft / Datadog / PagerDuty AIOps 的事件处理管线高度一致：

```
①Normalize（归一化：多源告警映射到统一 schema）
   → ②Deduplicate（去重：同签名重复告警折叠为一条 + 计数）
   → ③Enrich（富化：附加 CMDB/标签/runbook/拓扑上下文）
   → ④Correlate（关联：时间窗 + 共享属性 + 拓扑传播 + 内容相似度）
   → ⑤Roll-up（卷积为 Incident：计算优先级，抑制成员告警）
```

### 2.2 关联机制的产品实现

- **BigPanda**："Open Box Machine Learning" 营销点——**可解释的关联规则**（correlation recipes：同主机/同应用/N 分钟窗口的规则式聚类）而非黑盒模型；incident 内做根因打分（拓扑 + 历史 + 变更数据标记"主嫌疑告警"）。
- **Moogsoft**：聚类输出叫 "Situation"（= 本项目的 incident 概念）；算法含相似度聚类 + recipe 规则聚类 + 显著性评分。
- **Datadog Watchdog**：基线学习自动异常检测 + 根因假设，强项在"无阈值发现异常"。
- **PagerDuty AIOps**：事件编排（Event Orchestration）在 paging 之前完成去重/分组/富化；suppressions + 维护窗口防止计划内工作误 page。

### 2.3 SRE 告警原则（Google SRE《Alerting》章）

- **症状告警优先于原因告警**：page"用户正在感受的"（延迟/错误率），ticket 化"原因性的"（磁盘即将满）；本项目告警规则以资源阈值为主，属原因告警为主——因为 node-exporter 只有宿主机视角，缺业务症状指标（呼应"观测深度"缺口）。
- **多窗口多燃烧率**：基于 SLO 的 fast burn（快燃烧=立即 page）与 slow burn（慢燃烧=工单）双轨——本项目完全没有 SLO 概念，告警是纯静态阈值。
- **每个 page 必须可行动**：收到 page 的人应能立即做点什么；不可行动的告警降级为 ticket/邮件。

### 2.4 对照本项目：管线覆盖度

| 业界管线段 | 本项目实现 | 缺口 |
|-----------|-----------|------|
| Normalize | **缺失**（只接 Alertmanager 原生格式） | 多源接入（Zabbix/云监控）需要适配层——当前单源场景不痛 |
| Deduplicate | fingerprint 去重 + 抖动复用 | ✅ |
| Enrich | 服务名提取 + ALERT_SERVICE_MAP（轻量 CMDB 富化）+ 变更事件 | 服务重要性矩阵（影响分级）缺失 |
| Correlate | fingerprint 恒等 + 服务滑动窗归入（时间 + 属性） | **拓扑传播关联**（跨服务碎片问题）、变更锚定关联——数据已在系统（拓扑 JSON / get_recent_changes），路由层未消费 |
| Roll-up | incidents 实体 + 计算最高 severity | **主嫌疑告警标记**（BigPanda 式 culprit scoring 的规则版：incident 内标注哪条告警最可能是根源）|
| （增值）抑制 | severity 门槛 + 抖动复用 | **维护窗口/静默感知**：计划内变更期间发生的告警应标记 planned——`get_recent_changes` 数据可反向用于降噪 |

**一个重要的行业验证**：BigPanda 把"可解释的关联规则"作为核心卖点（Open Box ML），Moogsoft 也是算法 + 规则混合——**本项目选择规则式、可解释的关联（而非黑盒聚类）与业界头部产品的产品哲学一致**，这可以作为设计决策的外部佐证。

## 三、值班与响应实践

- **升级策略（Escalation Policy）**：多层升级 + 超时转交，保证告警永不静默死亡——本项目告警推飞书后无认领无升级，告警死亡无感知。
- **Runbook 与服务绑定**：PagerDuty 实践是 runbook 直接 attach 到 service，告警触发时自动附上"第一步做什么"。**本项目已有 `service + doc_type=sop` 的精准检索能力，等价能力只差"诊断卡片自动附 runbook 链接"一步**——低成本高价值。
- **值班卫生**：轮换、影子值班、明确的 override 规则——超出本项目范围（无人员管理域）。

## 四、复盘与知识管理（blameless 文化）

### 4.1 业界标准复盘结构

Google SRE《Postmortem Culture》的 blameless 原则（假设每个人在当时信息下都做了合理决策，追系统性原因不追个人）+ 标准文档结构：

```
Title / Summary（一句话概括）
Impact（影响：用户数/时长/金额——量化）
Timeline（时间线：检测/响应/恢复的关键时刻，含决策点）
Root Cause（根因，含触发条件与未被发现的理由）
Resolution（怎么恢复的）
Action Items（改进项：owner + deadline + 状态跟踪）
Lessons Learned（学到了什么）
```

**两个容易流于形式的点**（SRE 书明确指出）：复盘写完不跟踪 action item 完成率 = 白写；复盘只在出大事后写 = 学习密度不足（小事故也应复盘，且模板从简）。

### 4.2 对照本项目

本项目自动生成的恢复摘要目前只覆盖 Timeline + Root Cause + 建议三段。**对齐业界模板的改造点**：

1. **Impact 量化**：事故已有起止时间/告警级别/服务——缺"影响描述"字段（影响接口/用户范围），可从告警 annotations 或人工补充获得；
2. **Action Items 结构化**：复盘草稿的"后续建议"应结构化为 `{item, owner, deadline, status}` 列表落库，跟踪完成率——这是知识闭环的最后一公里（行动项不跟踪，复盘不产生价值）；
3. 复盘草稿 → 知识库入库时带上事故元数据（incident_id / 指纹集 / 诊断历史 ID），让下次诊断能引用"该事故的历史处理记录"。

## 五、AIOps 产品格局与本项目定位

| 产品 | 核心能力 | 与本项目的关系 |
|------|---------|---------------|
| Datadog Watchdog | 无阈值基线异常检测 + 根因假设 | 本项目用静态阈值规则，Watchdog 式基线学习是远期方向 |
| PagerDuty AIOps | 事件编排降噪 + 自动优先级 + 抑制 | 本项目的 severity 门槛/抖动复用是同类能力的轻量版 |
| BigPanda | 可解释关联规则 + incident 根因打分 | **设计哲学一致**（Open Box 可解释）；根因打分可借鉴为"主嫌疑告警标记" |
| Moogsoft | Situation 聚类 + 工作流 | Situation ≈ 本项目 incident |
| IBM Watson AIOps | 拓扑 + 日志关联 | 拓扑关联是本项目的已排期演进项 |

**定位结论**：业界产品的共同边界——**辅助人类判断而非替代**（证据聚合、降噪、假设生成），没有产品宣称"自动修复根因"。本项目的定位（"告警响应初期的信息聚合与假设生成"）与业界能力边界一致，且"增量重诊 + 事故生命周期 + 证据充分度"的组合在轻量/开源方案中少见，是差异化点。

## 六、可观测性标准（RED / USE / SLO / OTel）

- **RED 方法**（服务级：Rate / Errors / Duration）与 **USE 方法**（资源级：Utilization / Saturation / Errors）是指标目录的两大规范。本项目的服务 mock 指标（qps/error_rate/p99）恰好是 RED 形态，node-exporter 是 USE 形态——真实接入时按此规范整理指标目录即可，无需新增方法学。
- **SLO / Error Budget**：业界告警的终态语义是"对 SLO 的燃烧率"（fast burn → page，slow burn → ticket），静态阈值告警（CPU>80%）是过渡形态。**引入 SLO 需要先定义 SLI（哪些指标是服务质量的真相）**——对项目是较大语义升级，记录为演进方向。
- **OpenTelemetry**：tracing 缺失已知（跨服务诊断的根因缺口之一）；OTel 标准化的价值在"指标/日志/链路统一语义"，真实接入期建议直接采 OTel SDK 而非自造指标命名。

## 七、自动化修复的边界（Human-in-the-Loop）

业界共识的自动修复白名单标准：**确定性 + 低风险 + 可回滚**的动作才可自动化（重启进程、水平扩容、切流量），且生产环境必须过审批流（变更管理域）。本项目的 `create_incident_ticket`（诊断 → 工单 → 人工执行）定位正确——**"写操作的自动化"不应是本项目的下一步**，工单/审批集成才是正确方向（把"建议"变成"带审批的动作提案"）。

## 九、对既有设计决策的外部验证

调研带来三个"业界佐证本项目选择"的点（面试叙事可引用）：

1. **规则式可解释关联**：BigPanda 的核心卖点 Open Box ML 与本项目"规则式、可解释、宁拆分不污染"的路由哲学一致；
2. **辅助而非替代**：全部头部 AIOps 产品的能力边界都是"证据聚合 + 降噪 + 假设生成"，无产品宣称自动修根因——本项目的定位表述与业界能力边界一致；
3. **告警管线五段架构**：本项目的 fingerprint 去重/富化/关联/roll-up 覆盖了业界管线的 4/5 段（缺 normalize——单源场景不痛），架构位置正确。
