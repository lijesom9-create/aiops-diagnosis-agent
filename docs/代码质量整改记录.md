**补记（回归修复，2026-09-05）**：T3-A 首提后跑 `tests/test_agent_graph_flow.py` 等回归发现 **9 失败**，两层根因：

1. 抽取证据方法时把它们的 `@staticmethod` 装饰器残余留在了 agent.py —— 11 处悬空装饰器误加到实例方法上（`_count_message_tokens`、`_get_sufficiency_for_run`、`_build_system_prompt`），导致 `self` 方法被当成静态方法，"缺 state" 报错。→ 已全部移除，仅保留 3 处本就合法的 `@staticmethod`。
2. 被抽方法原本是 `LangGraphAgent` 的 `@staticmethod`，被 **6 个非生产调用方**（测试/脚本/评测）以 `LangGraphAgent._xxx()` 直接引用，抽离后类属性消失 → `AttributeError`。→ 已把这些调用方改为 `from app.langgraph_agent.evidence import ...`（test\_evidence\_parse、test\_agent\_graph\_flow、test\_business\_features、test\_reasoning\_layer、scripts/verify\_agent\_diagnosis、evaluation/verify/verify\_citations）。
3. **教训**：抽静态方法出类时，需全局搜索 `ClassName._method()` 调用方（含 tests/eval/scripts），不能只看编译/类内残留——compileall 对"类属性访问运行时才失败"不报错。

**验证**：compileall 通过；`test_agent_graph_flow + test_business_features + test_reasoning_layer` **51 passed**。

## 二·补、T3-B①：拆分 database.py——users+content 抽为 Mixin ✅

**对象**：`backend/app/core/database.py`（2009 行，单类 `Database`，约 110 方法，双后端：MongoDB / 内存）

**方案**：Mixin 组合（保持 `get_db()` 对外不变）。迁移第一批 `users+content`：

- 新建 `app/core/db_utils.py`：搬出 3 个无依赖 helper（`escape_regex`/`clean_mongo_doc`/`clean_mongo_docs`），供 mixin 与 database.py 复用，避免循环导入；database.py 顶部 re-export（保持 `from app.core.database import clean_mongo_doc` 兼容）。

**边界与工具**：方法行范围用 `ast` 精确取（含装饰器/docstring），不用正则枚举（正则对多行/嵌套边界不可靠——T3-A 的教训）。

## 二·补、T3-C：unified\_store.py 保守拆分——抽纯函数为 store\_utils ✅

**对象**：`backend/app/knowledge/unified_store.py`（2037 行，核心 `UnifiedKnowledgeStore` 类 1616 行 / 40 方法）。

**前置评估（为什么不照搬 database.py 的 Mixin 全拆）**：与 Database 的"天然按业务域分块"不同，`UnifiedKnowledgeStore` 的检索主流程高度内聚（search→\_vector\_search→\_rrf\_fuse→\_select\_rerank\_candidates→\_rewrite\_query 一路互调），且 `__init__` 承载大量实例状态（embedding/reranker/CLIP/多级缓存/双 store）。全拆会切成"一堆互调方法的中层类"，反而损可读性，且触检索语义硬约束、回归风险高。**故采用用户选定的保守拆**。

**方案（尽力保持行为逐字节等价）**：

- 新建 `app/knowledge/store_utils.py`：迁出 6 个**无状态纯函数**（不访问 self）：`merge_filters` / `match_metadata_filter` / `build_visibility_filter` / `build_child_filter` / `rrf_fuse` / `tokenize`。verbatim 搬移，递归改自引用模块函数。

- `UnifiedKnowledgeStore` 保留同名**薄委托方法**（`@staticmethod` 或按原样 instance 方法，签名不变），把逻辑转调 store\_utils。这样**所有既有调用点零改动**：内部 `self._merge_filters(...)`、类级 `UnifiedKnowledgeStore._match_metadata_filter(...)`（本文件递归 + 测试文件 4 处）、外部 `self._store()._build_visibility_filter(...)` 全部保持可用 → 对外契约稳定、无需改任何业务调用方。

**导入自检**：

- `_tokenize` 用到 `re`——搬走后 unified\_store 在 `QueryRewriter`（`re.search/re.escape`）仍用，故 `import re` 保留不删。

- `_tokenize` 内 `jieba` 为局部 import，随体搬走，store\_utils 仅在需要时触发。

- store\_utils 仅依赖 `typing`+`re`（及惰性 jieba），无循环导入风险。

**委托一致性验证**：委托方法 vs 模块函数对相同输入输出逐项相等（merge\_filters/match\_metadata\_filter/tokenize/rrf\_fuse 抽样比对 OK）；delegator parity OK。

**验证**：compileall 通过；ruff（unified\_store.py + store\_utils.py）全绿；检索相关测试 `test_retrieval_eval`/`test_reranker_maxp`/`test_generation_eval`/`test_execution_reliability` **22 passed**；全量 `tests/` **486 passed, 3 skipped**（仅余既有 checkpoint 依赖缺失 2，同基线一致）。
